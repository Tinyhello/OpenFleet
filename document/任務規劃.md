# OpenFleet 工廠資源調度系統：討論草案

更新日期：2026-10-09
狀態：P1、P2 已實作；後續階段需求討論中；Codex 負責規劃文件，實作交由 Claude。

## 專案主要目標：將 4 年 C#／Unity 經驗轉化為 .NET 技能語言

使用者已有 4 年 C#／Unity 開發經驗。本專案的主要目的，是以既有經驗為基礎，透過工廠資源調度情境，系統性整理、內化並熟練 .NET 後端開發的概念、設計方式與技術表達。

工廠調度系統是學習與驗證的載體。選型與任務範圍應優先支持使用者理解設計理由、對應既有經驗，並能用 .NET 後端的語言解釋與應用；功能完成度之外，也需要檢查是否真正掌握相關能力。

使用者已確認目標優先順序：第一為 .NET 系統性學習；第二為可上雲展示的作品集。場景為生產「藥片衝擊模具」的模擬機械加工廠，以 AGV 調度為主，包含倉儲、自動下單、自動給料，機台生產排程列入後續範圍。

後續討論與交給 Claude 的任務規格，建議附上以下學習對照。這些是可銜接的經驗，不代表兩側機制完全相同：

| 既有 C#／Unity 經驗 | 對應的 .NET 學習重點 | 本專案可用的練習情境 |
| --- | --- | --- |
| 元件拆分、物件協作與生命週期 | 依賴注入、服務責任、Singleton／Scoped／Transient 生命週期 | 拆分派工服務、MQTT client 與資料存取；理解 DbContext 作用域 |
| Update、Coroutine、非同步載入 | async／await、CancellationToken、BackgroundService 與執行緒模型 | MQTT 消費、派工與服務停止；區分 Coroutine 與非同步 I/O |
| 遊戲狀態機與事件通知 | 領域模型、狀態轉移、應用服務與整合事件 | 任務由待派工到完成，驗證每次狀態改變是否合法 |
| ScriptableObject、序列化與存檔 | Entity、DTO、關聯式資料建模、EF Core 與 Migration | 區分設定、API 契約、MQTT 契約與持久化資料 |
| 多物件共享狀態與操作順序 | 資料庫交易、樂觀並行控制、冪等性 | 防止重複占車、重送事件與併發派工 |
| Unity 除錯與測試 | 結構化日誌、單元測試、整合測試及可觀測性 | 追蹤一筆任務經 API、MQTT 到資料庫的完整過程 |

建議每個階段記錄：既有經驗對照、後端新增概念、選型理由、失敗情境，以及使用者能否自行解釋與調整設計。上述學習安排為提案，細節仍待討論。

## 2. 已選定業務場景與範圍

產品：藥片沖模；一件產品為一套，包含上沖、下沖及圓形中模。場域：模擬機械加工廠。各零件的加工路線與容量計數單位仍待細化，不能直接將一套產品當作一個加工零件。

使用者提供的流程：鐵件原物料 → 粗加工 → 精加工 → 淬火／回火 → 電鍍 → 拋光後處理 → 品管檢驗 → 必要時反工 → 包裝 → 出貨。

此流程作為本專案的模擬需求，不推定為所有實際產品的標準製程。各站是否廠內作業、是否委外，以及反工返回的製程，由後续討論決定；不自行補入加工參數。

| 範圍 | 優先順序 | 待定義內容 |
| --- | --- | --- |
| AGV 搬運與物料流轉 | 核心優先 | 搬運單位、派車、取料／卸料、站點交接 |
| 倉庫自動存儲 | 整體範圍內，階段待確認 | 儲位、入出庫、預約、搬運與存取設備交接 |
| 自動給料 | 整體範圍內，階段待確認 | 製程需求、庫存預留、目的站容量與搬運需求 |
| 自動下單 | 已確認包含採購單與生產工單 | 先建立流程；單據欄位、審核及詳細規則留待下一步 |
| 機台生產排程 | 已納入，低於核心調度 | 可加工機台、容量、時段、優先級與工序相依性 |
| 雲端作品集展示 | 第二目標 | 網址直接觀看或桌面 Unity 連雲端；部署與展示隔離 |

生產工單、製程作業、搬運任務與採購單應各自有明確責任與狀態。AGV 負責把物料送到站點；機台排程負責決定何時、由哪台機器加工，兩者透過需求與完成事件銜接。

## 3. 建議分階段情境

已確認 MVP 方向：以最小功能跑通完整流程，未定細節留空並在後續與使用者補齊。原料倉 → 粗加工 → 精加工的短流程可作內部開發步驟，但不是 MVP 的最終交付範圍。

本輪詳細討論見 [AGV能力與展示方案.md](AGV能力與展示方案.md)，內容包括複雜度邊界、補料範例與雲端展示選項，均未視為方案批准。

MVP 流程涵蓋採購／到貨／入庫與生產工單的基本銜接，以及原料 → 粗加工 → 精加工 → 淬火／回火 → 電鍍 → 拋光 → 品管（需要時反工）→ 包裝 → 出貨。先保留各站的基本輸入、批次作業與輸出，細部機構、單據及排程後續細化。站點數與未定規則不自行補成已確認需求。

已確認以批量進行；批內是否逐件加工、整批完成後才放行，以及上／下沖／中模如何配套仍待細化。固定加工時間與单機 FIFO 只是可選的模擬簡化，尚未定案。

### 2026-09-26 已確認調度規則

- 料箱與托盤配置於取料／取件處。使用後須歸還；若下個任務類似且可沿用，才可帶著載具銜接。相容條件與精確歸還位置待定，不能在卸料完成後一律把車輛視為可執行任意任務。
- 多車僅分攤數量：例如單車容量 30、需求 40，可拆成 30＋10；不包含兩車共同承載同一料件。
- .NET 負責狀態與運算，Unity 負責顯示。交通亦須模擬，演算法與詳細交通規則依使用者要求留待實作後討論。
- 待加工料容量為 30；完工件容量分 30 與 45，依桿徑粗細區分。桿徑對照及按零件／套數計算的單位待定；兩種容量不能混用。
- 派工優先順序：搬完成品 → 送刀具 → 缺料補料。此處完成品是否包括每道工序的已加工件，留待細化。
- 無可用車輛時任務等待，記錄缺車時間與所屬工序。等待起訖、累計方式及時間單位待定；建議保存等待區間供後續統計。
- 設置 AGV 充電維護區；位置、席位、充電門檻、耗時與維護流程待定。
- 小型 AGV 僅配送刀具，換刀由其他設備執行。

第一版候選功能：

1. Unity 顯示簡化 3D 工廠、站點、車輛、路線與狀態顏色。
2. Unity 操作面板可建立任務、查詢任務清單及車輛詳情。
3. 後端支援手動指定車輛，以及自動派工。
4. 自動派工先過濾載重、載具與站點相容性，再依優先級、建立時間與可達距離挑選可用車輛；平手以固定規則決定。
5. 保存任務、派工、狀態轉移與失敗原因。
6. 展示離線、指令逾時、重複訊息及服務重啟後的狀態恢復。
7. 顯示待派工數、執行數、完成数與車輛利用情形；統計定義另行確認。

整體範圍另需包含：批次追蹤、基本庫存與儲位、自動入出庫／給料、品管與反工、自動下單，以及後續機台排程。每一項的深度與交付階段待確認。

首階段暫不納入：真實 PLC／AGV 控制、外部 MES／ERP 串接、多工廠、採購金流、AI 最佳化、高擬真物理與正式生產可用性承諾。多車避碰與交通管制需在多車展示前選定模擬深度。

交通模擬已納入，具體交通策略延後討論。MVP 需標示已實現與未實現的交通行為；有移動動畫不代表已完成交會、壅塞或死鎖處理。

## 4. 技術分工與候選選型

| 層級 | 候選技術 | 責任／選擇理由 | 待確認事項 |
| --- | --- | --- | --- |
| 視覺化 | Unity，桌面版／WebGL 待選 | 場景、動畫、互動、狀態呈現 | Unity 版本、2D／3D、雲端展示是否需免安裝 |
| Unity 通訊 | Unity 相容 MQTT client | 訂閱 .NET 狀態供視覺化，不持有設備模擬權威狀態 | 「Unity-MQTT」是否指定某個套件 |
| 應用後端 | ASP.NET Core Web API，.NET 10 候選 | 資源查詢、任務建立、派工規則、驗證 | 開發環境、部署平台與版本 |
| 背景處理 | BackgroundService | MQTT 消費、派工迴圈、逾時檢查 | 初期與 API 同程序，之後再評估拆服務 |
| 後端 MQTT | MQTTnet | 連線 Broker、收送訊息 | 套件版本在批准後驗證並鎖定 |
| 訊息中介 | Mosquitto 候選 | MQTT Broker | 本機／Docker、連線權限 |
| 資料存取 | EF Core + PostgreSQL 候選 | 關聯資料、交易與派工一致性 | 若有 SQL Server 限制可改選 |
| 開發啟動 | Docker Compose 候選 | 啟動 Broker、資料庫與後端 | 是否可使用 Docker Desktop |

Unity 與 ASP.NET Core 不必使用相同 .NET 執行環境；以版本化 JSON 契約交換資料，避免讓 Unity 直接依賴後端 EF Entity。

M2MqttUnity 是候選之一，但原始專案列出的測試版本較舊，不能僅依 README 保證現代 Unity、TLS 或 IL2CPP 相容。若使用者指定套件，批准實作後先做小型連線驗證。

WebGL 受瀏覽器網路限制，需要另行確認 MQTT over WebSocket 與 Unity client 支援，不能直接沿用桌面 TCP 方案。Windows 桌面版可作為學習階段候選，但上雲展示是否要求免安裝、直接在瀏覽器觀看仍待確認，尚未選定最終平台。

架構提案：先以單一 ASP.NET Core 應用依領域分模組，逐步建立訂單／生產、庫存／倉儲、搬運調度、品質及模擬的責任邊界。先學會模組協作、交易與訊息一致性，再依需求評估是否拆程序；不因功能多就預設拆成微服務。

第一版已有 MQTT 時，暫不額外引入 SignalR；若後續需要網頁管理台，再評估即時推播方式。

## 5. 建議資料流與責任界線

```text
Unity 操作面板 ── HTTP ──> ASP.NET Core ── 交易 ──> 資料庫
                              │
                         MQTT 派工指令
                              ↓
                         MQTT Broker
                              ↓
                       設備／設備模擬器
                              │
                         MQTT 設備回報
                              ↓
                  後端驗證、保存並發布狀態
                              ↓
                     Unity MQTT 訂閱呈現
```

- 後端擁有任務與派工狀態的最終決定權；Unity 不直接修改資料庫。
- 已確認由 .NET 持有設備狀態、運動、加工與調度運算，Unity 顯示並可傳送操作請求；調度與設備模擬的邏輯責任分開，同一車輛僅有一個狀態來源。是否拆成獨立程序仍待技術設計。
- 車輛位置遙測與業務完成回報分開處理；動畫抵達不直接代表資料庫任務完成。
- Unity 首次連線與重連使用 HTTP 快照與 MQTT 狀態更新；需設計訂閱緩衝、版本對齊與缺口補取，具體順序待定。
- MQTT 收訊後透過佇列切回 Unity 主執行緒更新場景。

## 6. 後端資料結構草案

以下為概念模型，待範圍確認後才定義正式 C# 類別、欄位型別、索引與 Migration。

| 實體 | 候選欄位 | 關係與規則 |
| --- | --- | --- |
| Factory | Id、Name | 包含站點、車輛與路網 |
| Station | Id、FactoryId、Code、PositionX/Y/Z | 搬運起點／終點；定義公尺與座標轉換 |
| RouteEdge | Id、FromStationId、ToStationId、Distance、Enabled | 明確定義方向；供可達性與最短路徑計算 |
| Vehicle | Id、FactoryId、Code、OperationalStatus、LastSeenAt、Version | 靜態資料與目前業務狀態；位置另存最新遙測 |
| TransportTask | Id、FromStationId、ToStationId、Priority、Status、CreatedAt、Version | 第一版一趟任務對應一台車；起終點需可達 |
| Assignment | Id、TaskId、VehicleId、Attempt、Status、AssignedAt | 任務可有多次嘗試；同一時間只能有一筆有效派工 |
| TaskEvent | Id、TaskId、AssignmentId、FromStatus、ToStatus、Reason、OccurredAt | 保留任務狀態歷史 |
| VehicleTelemetry | VehicleId、SessionId、Sequence、Position、ReportedAt、ReceivedAt | 預設保存最新狀態；歷史保存週期另訂 |
| OutboxMessage | Id、Topic、Payload、PublishedAt、Attempt | 與派工同交易建立，避免已存任務卻未送出指令 |
| InboxMessage | ProducerId、MessageId、ProcessedAt | 唯一鍵去重，避免 MQTT 重送產生第二次業務效果 |

共同規則：ID 使用 UUID 候選；時間使用 UTC／DateTimeOffset；狀態用明確 enum；API DTO、MQTT DTO 與資料庫 Entity 分開。

派工時以資料庫交易及唯一性／並行控制防止兩個工作者同時占用同一車輛。具體索引方式依資料庫選型決定。

任務狀態候選：Pending → Assigned → Executing → Completed，另有 Failed、Cancelled。指令等待設備接受的狀態記錄於 Assignment；完成回報需符合目前 Assignment 與合法狀態轉移。

第一版取消建議僅允許 Pending；執行中取消牽涉停車與設備確認，需另外批准範圍。指令逾時先標記待確認並暫停車輛再派工，不直接把可能仍在執行的任務交給另一台車。

### 完整工廠場景所需的模型擴充（概念提案）

| 模組 | 候選模型 | 核心責任 |
| --- | --- | --- |
| 產品與製程 | ProductDefinition、ProcessRoute、ProcessStep | 產品規格、製程順序與版本；工單保留使用的版本 |
| 生產執行 | ProductionOrder、MaterialLot、OperationExecution | 區分工單、實際物料批次與每次加工；反工保留新一輪執行紀錄 |
| 庫存與倉儲 | StorageLocation、InventoryMovement、MaterialReservation、StorageTask | 追蹤位置、數量、預留、入出庫及存取設備作業 |
| 搬運交接 | LoadUnit、TransportTask、TransferConfirmation | 托盤／料箱與批次關聯；取料、載運、卸料分階段確認 |
| 機台資源 | Machine、MachineCapability、StationBuffer | 加工能力、狀態與入站容量；詳細時段排程後續擴充 |
| 品管與反工 | InspectionResult、ReworkInstruction | 保存判定與原因、返回工序、反工次數；避免無限循環 |
| 下單 | PurchaseOrder、ProductionOrder（細節下一步） | 已確認採購與生產兩種流程；採購到貨不等於已入庫或可給料 |
| 車型與載具 | VehicleType、VehicleCapability、Carrier、CarrierCompatibility | 記錄車型能力、實體載具及目前裝備，派工前驗證相容性 |
| 需求拆分與補料 | TransportRequest、TransportTask、ReplenishmentPolicy | 一筆需求拆多趟任務，追蹤已分配／在途／已交付量，控制機邊容量 |
| 產品組成 | ProductComponent、ComponentLot（候選） | 區分上沖／下沖／中模與整套產品；配套規則待定 |
| 載具周轉 | CarrierReturnTask／CarrierContinuation（候選） | 歸還或相容任務沿用，追蹤載具位置與占用 |
| 缺車紀錄 | ResourceWaitInterval（候選） | 關聯任務及工序，保存無可用車的等待區間；不與缺料／交通等待混算 |
| 充電維護 | ServiceArea、VehicleServiceState（候選） | 區域與車輛充電／維護狀態，細部規則留空 |

需在詳細設計時維持的規則：

- 同一搬運單位同時只在一個實體位置，包含倉位、站點及 AGV 車上；庫存預留不等於已經搬走。
- 搬運完成、入庫完成與加工完成是不同事件；必須由對應交接確認推動狀態。
- 自動給料需先確認前置製程完成、物料可用與目的站容量；無容量時等待，不無限生成搬運任务。
- 品管未放行不能直接流入出貨。反工返回何站、是否需重新檢驗與最多次數需明確規則。
- 同一批次可拆成多個搬運單位並保留批次關聯；分量運輸不必自動建立新生產批號。合批、部分合格與報廢規則另訂，數量與位置必須可追溯。
- 自動下單觸發需有穩定業務識別及重複防護，避免每次檢查庫存都建立新單。

## 7. MQTT 契約草案

| Topic 候選 | 方向 | 用途 |
| --- | --- | --- |
| openfleet/v1/{factoryId}/vehicles/{vehicleId}/commands | 後端 → 模擬器 | 派工指令，不使用 retained |
| openfleet/v1/{factoryId}/vehicles/{vehicleId}/events | 模擬器 → 後端 | 接受、開始、完成、失敗 |
| openfleet/v1/{factoryId}/vehicles/{vehicleId}/telemetry | 模擬器 → 後端 | 座標、目前運作狀態 |
| openfleet/v1/{factoryId}/state/tasks/{taskId} | 後端 → Unity | 經後端確認的任務狀態 |
| openfleet/v1/{factoryId}/state/vehicles/{vehicleId} | 後端 → Unity | 經後端確認的車輛狀態 |

共用欄位候選：schemaVersion、messageId、producerId、correlationId、occurredAt、payload。指令再帶 commandId、assignmentId、expiresAt；回報需帶相同 assignmentId；遙測使用 sessionId + sequence 處理重連與亂序。

狀態 Topic（P1 已實作）：payload 帶 stateEpoch（後端每次啟動換新值）與 version（同一 epoch 內遞增）；顯示端 epoch 相同才比較 version，不同則直接採用新狀態。

- 指令與事件建議 QoS 1，應用端以穩定 ID 去重；MQTT 傳輸確認不等於設備執行成功。
- 高頻位置可選 QoS 0；初始候選每秒 5 次，Unity 插值顯示，實際頻率待確認。
- 心跳、離線與逾時的秒數需要依展示／真實設備情境設定。
- 連線帳密與 Topic 權限按顯示端、模擬端、後端角色區分；跨主機部署時定義 TLS。
- 設備重送同一完成事件不得新增完成紀錄或重複釋放資源。

- [MQTTnet 原始專案](https://github.com/dotnet/MQTTnet)：後端 MQTT client 候選。
- [M2MqttUnity 原始專案](https://github.com/gpvigano/M2MqttUnity)：Unity MQTT 候選及已記錄的平台測試範圍。
- [Unity Web 網路限制](https://docs.unity3d.com/6000.0/Documentation/Manual/webgl-networking.html)：瀏覽器目標需另行設計網路連線。
- [OASIS MQTT 5.0 規格](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)：QoS、保留訊息及協定行為；最終協定版本仍需配合 client 確認。

本草案中的產品範圍、模型與技術組合為設計建議，不是上述來源的既定要求。
