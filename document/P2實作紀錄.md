## 2. 做了什麼

```text
Unity 面板 ── HTTP ──> ASP.NET Core ── 交易 ──> PostgreSQL
 (設定、建立批次、批次清單)   │  ├ 加工迴圈：到期就完成、建立下一趟搬運
                              │  ├ 派工迴圈：選車、寫入派工＋Outbox
                              │  └ Outbox 發送：指令 → MQTT
                              ↓
                         Mosquitto ──> 模擬器：沿走道開到取料點、交接、開到卸料點
                              ↑                    │
                              └── Accepted／Loaded／Completed（Inbox 去重後才改資料）
```

一個批次的生命週期：

1. `POST /api/lots`：在原料倉建立批次（模擬收料），同時建立「原料倉 → 粗加工」的搬運任務。
2. 派工迴圈把任務派給可用的車，指令經 Outbox 送出。
3. 車輛回報 `Accepted` → 開到取料點、交接後回報 `Loaded`（批次改為在車上）→ 開到卸料點、交接後回報 `Completed`（批次改為在站內排隊）。
4. 加工迴圈讓機台開始加工；時間到了整批放行，建立送往下一站的搬運任務。
5. 精加工完成後送到暫存點（淬火／回火站入口），批次狀態為 `Staged`，流程結束。
6. 車輛沒有任務時回到充電維護區的車位。

## 4. 實作時做出的技術決定（Claude，可調整）

| 項目 | 目前做法 | 理由 |
| --- | --- | --- |
| 套件版本 | EF Core 10.0.12、Npgsql EF Core 10.0.3、PostgreSQL 17、Testcontainers 4.16 | 撰寫時的最新穩定版 |
| 模組切分 | 仍是單一 ASP.NET Core 專案，依資料夾分 `Fleet`／`Production`／`Transport`／`Data` | 任務規劃第 4 節：先學模組協作，不預設拆服務 |
| Migration | 啟動時自動套用，並補上缺少的示範資料（站點、工序、設定、車輛） | 開發階段方便；只新增缺少的列，面板改過的值不會被蓋掉 |
| 資料庫連不上 | 後端直接啟動失敗 | 沒有資料庫就無法保證任何業務狀態，和 MQTT 可以先降級不同 |
| enum 儲存 | 字串 | 直接查表看得懂；調整 enum 順序不影響舊資料 |
| 並行控制 | 批次、任務、派工用 PostgreSQL 的 `xmin` 當版本 | 不需要另外維護版本欄位 |
| 不重複占車 | 部分唯一索引：同一台車、同一個任務同時只能有一筆有效派工 | 由資料庫保證，兩個工作者同時派工時第二筆會被拒絕 |
| 一個位置 | 資料庫 check constraint：批次不是在站上就是在車上 | 程式寫錯時由資料庫擋下 |
| Outbox | 派工、任務狀態、歷史、待發送指令同一筆交易；另一個背景服務每 0.5 秒發送 | 不會出現「派工已存但指令沒送」 |
| Inbox | `(producerId, messageId)` 主鍵；去重和業務變更同一筆交易 | 取代 P1 的記憶體去重，重啟後仍有效 |
| 車輛位置 | 仍只放記憶體（`FleetStateStore`） | 每秒 5 次的高頻資料，不適合每筆寫資料庫 |
| 選車 | 先過濾（大型車、連線中、開放派工、沒有有效派工），再選離取料點直線距離最近的，相同時比 ID | 任務規劃第 3 節的候選規則 |
| 任務順序 | 依建立時間 | 見第 6 節待決定事項 1 |
| 目的站容量 | 已在站內排隊的數量＋已派工還沒卸料的數量＋本次數量 ≤ 待加工料容量，否則任務等待 | 對應補料文件的「已承諾未入站量」 |
| 完工件容量 | 完工件還沒被搬走時，機台不開始下一批 | 完工件容量 30／45 的對照還沒定，先保守處理而不是當成無限 |
| 倉庫與暫存點容量 | 沒有建模（資料表為 null） | 規則還沒定；暫存點接上淬火製程後再套用容量 |
| 指令逾時 | 10 秒沒有回覆 → 派工標記為 `Unconfirmed`，車輛與任務仍被占用，不改派 | 任務規劃第 6 節 |
| 設備拒絕 | 任務回到待派工；同一任務被拒絕 3 次後標記失敗 | 避免無限重派 |
| 加工模擬 | 後端內的背景服務，到期時間存在資料庫 | 機台的 MQTT 契約還沒設計；存資料庫讓後端重啟後能接續 |
| 車輛行駛路徑 | 先接上環狀走道，沿較短的方向走，再離開走道到目的地 | 路網（RouteEdge）與交通規則留到 P3 |
| 回車位 | `MoveTo` 指令，不是派工、不經 Outbox；收到搬運指令時可被取代 | 遺失了下一輪會重發，不需要保證送達 |
| 新增契約 | 指令 `Transport`／`MoveTo`、事件 `Loaded`、指令的 `pickup`／`destination` | 都是新增，沒有提高 `schemaVersion`；Unity 的契約 DLL 已同步 |
| 任務狀態 Topic | 還沒做 `state/tasks/{taskId}`，Unity 面板用 HTTP 每秒輪詢 | P2 的面板只需要清單；即時推播留到 P3 |
| 測試資料庫 | Testcontainers 啟動真正的 PostgreSQL，每個測試一個資料庫 | 要驗證的正是唯一索引、xmin 與交易，記憶體資料庫測不出來。跑測試需要 Docker |

### Unity 面板

| 項目 | 做法 | 理由 |
| --- | --- | --- |
| 技術 | UI Toolkit，介面全部在 `ProductionPanel.cs` 用 C# 建立，沒有 UXML／USS 檔 | 使用者建議 UI Toolkit；場景本來就是程式產生的，維持同一種做法 |
| 數值輸入 | 滑桿加輸入框 | 中文輸入法開著時，數字鍵會被輸入法攔截；滑桿用滑鼠就能調整 |
| 中文字型 | 執行時向作業系統要中文字型（微軟正黑體等） | 和場景標籤的做法一致；WebGL 沒有系統字型，屆時要改成隨專案附帶字型 |
| 資料來源 | 面板只呼叫 HTTP API，自己不保存業務狀態 | 後端是唯一的狀態來源 |
| 建置 | 新增選單 **OpenFleet → Build Windows Player** | 之前是用一次性的腳本建置 |

## 5. 驗證結果（2026-10-09）

- 自動化測試：55 個全部通過（P1 原有 25 個、P2 新增 30 個）。
  - 物料流程（真正的 PostgreSQL）：派工與指令同一筆交易、資料庫拒絕重複占車、舊版本寫入失敗、事件重送只有一次效果、亂序與別台車的回報被忽略、拒絕後重派與次數上限、逾時後不改派、加工時間未到不放行、完工件未取走不開始下一批、設定驗證。
  - 模擬器：搬運依序回報、重送的指令不重複執行、忙碌與過期時拒絕、搬運取代回車位。
  - 端對端（內嵌 MQTT broker＋後端＋模擬器＋PostgreSQL）：批次從原料倉走到暫存點，共 7 筆位置異動、2 筆加工紀錄、3 趟搬運。
- 手動驗證（真正的 Mosquitto 與 PostgreSQL）：
  - 建立批次後約 2 分鐘走完整個流程，位置異動的時間順序正確。
  - 流程結束後 `agv-01` 回到車位；啟動時 3 台車都自行開到充電維護區。
  - 批量設成 31 時回傳 HTTP 400 與原因。
  - 兩個 15 件的批次同時進行：共 9 趟搬運全部一次完成，後端沒有任何警告。
  - 加工進行中強制結束後端再啟動：加工紀錄的到期時間還在資料庫，重啟後接續，兩個批次都走到暫存點。
- Unity Windows Player（以模擬滑鼠操作驗證）：面板與中文顯示正常；點滑桿把批量改成 15、粗加工改成 45 秒後按「套用」，後端設定確實改變；「建立批次」會建立批次，清單隨狀態更新到「已送達 淬火／回火 暫存」。輸入框的鍵盤輸入沒有驗證成功：這台電腦的中文輸入法攔截了數字鍵，因此數值欄位改成滑桿加輸入框。

## 7. 已知限制

- 車輛離線或模擬器重啟時，進行中的搬運會停在當下的狀態（派工仍然有效），沒有對帳與恢復流程；待確認（`Unconfirmed`）的派工也沒有人工解除的方式。可以用面板的「清除示範資料」重來。
- 處理事件時若資料庫發生非並行衝突的錯誤，該則事件會被記錄後丟棄，不會重試（沒有 dead-letter）。
- 沒有交通規則：車輛沿走道走較短的方向，不會避讓其他車。單車驗證不受影響，P3 多車之前必須處理。
- 沒有拆批、沒有載具（料箱／托盤）、沒有刀具配送、沒有庫存預留。
- 車輛不知道自己載著什麼：Unity 畫面上車輛載貨與空車看起來一樣，站點也不顯示目前有哪些批次（只有面板清單）。
- `POST /api/demo/reset` 與所有 API 都沒有驗證，只能在本機使用；PostgreSQL 的帳密寫在 `docker/compose.yaml` 與 `appsettings.json`，上雲前要改。
- Unity 面板的輸入框在中文輸入法開啟時無法直接輸入數字，請用滑桿，或先切換到英數模式。

## 8. 修改：車速、上下料、逐件加工、換刀與進度條（2026-10-09）

使用者看過 P2 的畫面後提出 6 項修改。

### 使用者的要求與決定

| 項目 | 要求 | 決定（含本輪詢問的答覆） |
| --- | --- | --- |
| 1. 車速 | 依載運的內容物與數量不同；空車可以是原本的 2 倍 | 空車 2 m/s；載貨時依件數線性遞減，滿載 30 件時 1 m/s。不同內容物的差異等有第二種零件時再加 |

| 6. 刀具進度條 | 可以展開、收合，主要顯示加工進度 | 刀具列預設收合，按機台進度條下方的「刀具」按鈕切換；換刀時加工列直接變成「換刀」 |

### 實作重點

| 項目 | 做法 |
| --- | --- |
| 逐件加工 | 加工紀錄存「已完成件數」與「目前這一件何時開始」。每一輪把進度推算到現在：一件一件完成、到達壽命時開始換刀、換刀到期後從那個時間點繼續。所有時間點都由資料庫裡的時間推算，後端停機後一次補算的結果和持續執行相同 |
| 換刀 | 每個加工站一筆刀具狀態（已加工件數、換刀開始與到期時間）；換刀完成時新增一筆換刀紀錄。機台閒置時換刀也會照常結束；換刀中不開始下一批 |
| 備料區容量 | 加工中批次還沒做的件數仍算在備料區，派工檢查容量時一併計入（原本加工一開始就整批不算） |
| 指令 | 搬運指令新增件數、內容代碼與交接時間（件數 × 每件秒數），由後端決定、設備照做 |
| 遙測 | 新增活動（待機／行駛／上料／下料）、上下料進度、車上件數與內容；後端原樣轉成車輛狀態發給 Unity |
| 車上的貨 | 取料交接完成才算在車上（車速同時變慢），卸料交接完成才歸零 |
| 站點狀態 | 新增 `GET /api/stations/status`，Unity 每 0.5 秒輪詢一次；車輛的進度仍走 MQTT |
| Unity 進度條 | `StatusOverlay`：UI Toolkit 畫在螢幕座標，每個 frame 依攝影機重新定位；不需要額外的材質或世界座標 Canvas |
| 契約 | 都是新增欄位，沒有提高 `schemaVersion`；Unity 的契約 DLL 已同步 |
| Migration | `PieceMachiningAndTools`。產生器把兩個欄位誤判成改名，手動補上資料修正；既有資料庫升級後會得到上表的數值 |

### 驗證結果

- 自動化測試 60 個全部通過。新增：逐件計數與整批放行、到達壽命時暫停換刀、停機後一次補算的結果相同、備料區剩餘件數計入容量、指令帶入件數與交接時間、載貨時車速變慢並回報上下料進度。
- 手動驗證（真正的 Mosquitto、PostgreSQL 與 Unity Windows Player；為了縮短等待，暫時把上下料與加工調成每件 1 秒、粗加工刀具壽命 20 件，驗證後已還原）：
  - 既有資料庫升級後設定正確（上下料 5 秒／件、換刀 20 秒、加工 2 秒／件、刀具壽命 500／250）。
  - 車輛上下料時上方出現「上料／下料」進度條；載貨時車上出現料箱。
  - 機台顯示備料、成品、加工三列，加工中數字逐件變化（例如備料 19／成品 11／加工 11）；按「刀具」可展開刀具列（11/20）。
  - 到達刀具壽命時加工列變成紅色「換刀」並顯示百分比，備料與成品的數字停住。
  - 原料倉有料時顯示「待搬運 30 件」。

### 這次修改之後的已知限制

- 以預設值計算，30 件的批次一趟搬運要上料 150 秒＋下料 150 秒，整個流程約 18 分鐘。想看快一點可以在面板調小「上下料（秒／件）」。
- 加工進度每 0.5 秒更新一次、逐件跳動，進度條不是平滑移動。
- 換刀沒有刀具庫存、沒有配送：時間到就完成。
- 上料中車上還沒有貨、下料中貨還在車上；沒有「一件一件搬」的中間狀態。
- 機台進度條固定大小，畫面拉遠時會比機台大，站點靠得近時可能互相重疊。
- Unity 面板的滑桿只能表示整數；用 API 存了小數的設定時，面板顯示會四捨五入，按「套用」會存成整數。
- `PUT /api/settings` 是整份取代：沒有帶的數值欄位會被當成 0（上下料、換刀）或被拒絕（批量），`steps` 則只更新有列出的工序。

## 9. 測試用的模擬時間倍率（2026-10-09）

> 2026-10-10：整體的時間倍率已取消，改成測試模式與各站的專用倍率，見 P4實作紀錄第 5 節。以下是當時的紀錄。

使用者要求：增加一個測試用的按鈕，可以把遊戲時間加速 5 倍或 10 倍。

| 項目 | 做法 | 理由 |
| --- | --- | --- |
| 加速的對象 | 模擬的時間：車輛行駛、上下料、加工、換刀 | 狀態與運算都在 .NET，只加快 Unity 畫面沒有意義 |
| 不受影響 | 指令有效期限、離線判定、派工與加工的檢查間隔 | 這些是通訊與系統層面的實際時間 |
| 保存位置 | 後端記憶體（`SimulationSpeed`），後端重啟後回到 1 倍 | 測試用的設定不應該不小心留下來 |
| 傳給模擬器 | 後端以 retained 訊息發布到 `openfleet/v1/{factory}/state/simulation`；每次連上 Broker 都重發 | 模擬器是另一個程序；retained 讓晚啟動的模擬器也拿得到，重發可蓋掉 Broker 上的舊值 |
| 後端的作法 | 不改時鐘，把每件加工秒數與換刀秒數除以倍率 | 資料庫裡的時間仍是實際時間，紀錄不會錯亂 |
| 模擬器的作法 | 每一步推進的模擬時間＝實際時間 × 倍率 | 行駛與上下料一起變快；回報的車速仍是 1 倍時的數值 |
| 切換的瞬間 | 進行中的那一件從切換的時間重新計時 | 否則切到高倍率時，之前已經過的時間也會用新倍率計算，一口氣跳好幾件 |
| API | `GET /api/simulation`、`PUT /api/simulation`（`{"timeScale": 10}`，允許 1～20） | 面板只提供 1、5、10 三顆按鈕 |
| Unity | 面板上「模擬速度（測試用）」的 1×／5×／10× 按鈕，目前的倍率以底色標示 | 顯示的是後端回報的值 |

驗證：自動化測試 63 個全部通過（新增：倍率加快加工與換刀且切換時不會跳件、倍率同時加快行駛與上下料、倍率以 retained 訊息送達模擬器並拒絕超出範圍的值）。在 Unity Player 按 10× 後建立 15 件的批次：上料 15 件約 8 秒（1 倍是 75 秒），整個流程 66 秒（1 倍約 9 分半）。

已知限制：

- 10 倍速時車輛每次回報之間移動約 4 公尺，畫面上的車會被平滑處理切過轉角，看起來不是沿著走道走。
- 派工與加工的檢查間隔（1 秒、0.5 秒）不會跟著縮短，所以整體加速不到剛好 10 倍。
- 倍率切換只影響之後的進度；切換當下正在進行的換刀仍依開始時的倍率完成。
- 模擬器在後端沒有執行時會沿用最後收到的倍率。

## 10. AGV 目的地的動態虛線（2026-10-09）

使用者要求：加上一條動態虛線，顯示 AGV 準備前往的目的地。

| 項目 | 做法 | 理由 |
| --- | --- | --- |
| 路徑的來源 | 模擬器在遙測中回報「接下來要依序經過的點」（`route`，最後一點是目的地），後端原樣放進車輛狀態 | 路徑是模擬器規劃的；Unity 只負責畫，不自己猜路線 |
| 顯示的內容 | 行駛中：剩下的路徑。上料中：上料完成後到卸料點的路徑（預告）。下料中、待機：不顯示 | 「準備前往」包含還沒出發但已經確定的下一段 |
| 畫法 | `StatusOverlay` 用 UI Toolkit 的 Painter2D 畫在螢幕上；虛線的長度與間隔以世界座標計算後再投影 | 不需要另外準備材質與貼圖；虛線有透視感，跨過轉角時圖樣不中斷 |
| 動畫 | 虛線以固定速度往目的地方向流動；終點畫一個圓圈 | 只是動畫，和車速、模擬時間倍率無關 |
| 契約 | `VehicleTelemetry.Route`、`VehicleState.Route`，新增欄位，沒有提高 `schemaVersion` | 舊的接收端會忽略 |

驗證：自動化測試 64 個全部通過（新增：遙測帶出剩下的路徑、走過的點會消失、上料中預告下一段、下料與待機時沒有路徑；狀態複本不共用路徑清單）。在 Unity Player 上看過前往取料點的虛線、上料中預告往粗加工的虛線，以及車輛靜止時虛線仍在流動。

已知限制：

- 虛線畫在螢幕最上層，不會被機台或車輛遮住。
- 每筆遙測都帶完整的剩餘路徑（目前最多約 6 個點）；之後路網變複雜時應改成只在路徑改變時傳送。
- 回充電維護區的移動也會顯示虛線。
