# P5 實作紀錄：訂單與 BOM

## 1. 範圍與步驟

P5 把「建立批次」換成正式的單據：客戶訂單 → 生產工單 → 料框，並加上規格、BOM、原料庫存、切料與採購。使用者 2026-10-22 確認的規則：

- 客戶訂單與生產工單分兩層；客戶可以訂整組，也可以只訂單一零件（一行最多 300 組／300 支）。
- 一組沖模＝一支上沖、一支中模、一支下沖（依這個順序列出）。
- 桿徑大多只有 24 與 30 兩種；沖頭有很多規格與特殊形狀，大多對應到桿徑。桿徑是基底，沖頭規格繼承後覆寫自己的部分。
- 中模外徑 38，內孔跟著沖頭規格；一框支數跟同組的上下沖相同，電鍍一爐支數跟下沖相同。
- 原料是很長的 Φ40 圓棒，在切料站整根切完成備料，一根只切一種長度，多出來的備料入庫，下次同規格先用。一根約可切十幾支，切一支約 5 分鐘。
- 圓棒低於安全庫存時提醒，要不要補貨由人決定。圓棒不夠時不等料，先用現有的切、開始做，缺的部分到貨後再切。
- 品管報廢時在原工單註記，另開補做工單；補做又報廢，同樣記在主工單、再開一張。
- 品管 → 包裝 → 出貨；多出來的零件依規格與廠商收進成品倉。
- 整張訂單齊了才一起出貨，齊了就直接出；要分批必須有負責人同意，以完整的一組為單位，最多分一次，之後剩下的要全部到齊才出。
- 一組從下單到完成約三週到一個月；測試加速下讓觀看的人約 2～3 分鐘看完一個流程。

實作分成幾步，每一步做完先給使用者看：

| 步驟 | 內容 | 狀態 |
| --- | --- | --- |
| 1 | 規格與 BOM：桿徑、沖頭規格（覆寫）、品項、BOM 版本；零件順序改成上沖、中模、下沖；中模的一框與電鍍跟同組 | 完成（本節） |
| 2 | 庫存與採購：圓棒與備料庫存、安全庫存提醒、人工建立採購單、到貨入庫 | 完成（第 3 節） |
| 3 | 切料站：後端站點、Blender 模型、AGV 原料倉 → 切料站 → 粗加工 | 完成（第 4 節） |
| 4 | 客戶訂單與生產工單：取代建立批次、工單保存規格快照、重複送單只算一次、補做工單 | 完成（第 5 節） |
| 5 | 出貨改看整張訂單、負責人同意分批；成品倉變成真正的站點 | 未開始 |
| 6 | 測試加速：讓一個流程約 2～3 分鐘看完 | 未開始 |
| 7 | Unity 下單面板 | 未開始 |

## 2. 第 1 步：規格與 BOM（2026-10-22）

### 資料表

| 資料表 | 內容 |
| --- | --- |
| `RodSizes` | 桿徑 24、30：一框支數（45／30）、三種零件的備料長度 |
| `PunchSpecs` | 沖頭規格：指向一個桿徑，覆寫欄位（三種備料長度、粗加工與精加工每支秒數）可以留空，留空就沿用 |
| `Items` | 品項：整組、零件、備料、圓棒。每建立一種規格就產生 1 個整組、3 個零件、3 種備料；圓棒只有 `BAR-D40` 一種 |
| `BomVersions`、`BomLines` | 一個品項的一版 BOM。整組 → 上沖、中模、下沖各 1；零件 → 自己的備料 1 |

- 繼承用資料表達，沒有用 C# 類別繼承：新增一種規格只是多一筆資料，不用改程式。解析的規則寫在 `CatalogService.Resolve`：規格有覆寫就用覆寫，否則備料長度與一框支數沿用桿徑、加工秒數沿用製程設定。
- 備料 → 圓棒不是 BOM 的固定用量，而是切料規則：一根切幾支＝圓棒長 ÷ (備料長 + 切口)，無條件捨去。
- 品項代碼：整組是規格代碼（`P30-HX10`）、零件加 `-U`／`-D`／`-L`、備料再加 `-BLK`。
- BOM 的 (品項, 版本) 是唯一索引；改組成時新增一版、不改舊版。第 4 步的工單會記住開立時的版本，並保存解析後的規格（`ResolvedPunchSpec`），之後改規格或桿徑不影響已開立的工單。目前還沒有發新版的 API。
- 建立規格時，規格、7 個品項與 4 份 BOM 在同一筆交易寫入；代碼重複回 409，兩個請求同時建立同一個代碼時由主鍵擋下後到的那一個。

### API

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| GET | `/api/catalog/rod-sizes` | 桿徑與預設值 |
| GET | `/api/catalog/specs`、`/api/catalog/specs/{code}` | 規格與解析後的有效值，每個值標明是不是覆寫的 |
| POST | `/api/catalog/specs` | 建立規格（400 輸入錯誤、409 代碼重複） |
| GET | `/api/catalog/items?kind=part` | 品項，可依種類篩選（set、part、blank、bar） |
| GET | `/api/catalog/items/{code}/bom?version=` | BOM，不指定版本取最新一版 |
| GET | `/api/catalog/items/{code}/explosion?quantity=120` | 整組或單一零件展開：每種零件幾支、備料多長、一根切幾支、要幾根圓棒、多出幾支、每根剩多少 |

展開還沒扣現有庫存（庫存是第 2 步）。

### 改到的既有行為

- `ProductParts.All` 的順序改成上沖、中模、下沖。建立批次、面板顯示都跟著這個順序。
- 中模一框支數跟同組的上下沖相同：Φ24 那組一框 45 支（原本固定 30）。
- 中模電鍍一爐支數跟下沖相同：Φ24 那組 56 支（原本比照 30 mm 的 40 支）。

### 示範值與 Claude 自己決定的部分

- 圓棒長 1.5 m、切口 3 mm、各零件的備料長度（Φ30：上沖 110、中模 90、下沖 95 mm；Φ24：100、85、88 mm）都是示範值，讓一根切出十幾支。使用者有實際數字再換。
- 四個示範規格（`P30-RD12` 圓形、`P30-HX10` 六角、`P24-SQ08` 方形、`P24-SK01` 鍵形）的名稱與覆寫值是 Claude 編的，用來展示「沿用」與「覆寫」：六角的精加工 90 秒、鍵形的精加工 120 秒與上沖備料 115 mm。
- 規格能覆寫的欄位先只有三種備料長度與粗加工、精加工秒數。
- 規格代碼限 3～24 個字元的大寫英數與 `-`（輸入會轉成大寫）；備料長度要能從一根圓棒至少切出一支。

### 驗證

- 自動測試 113 個（新增 8 個；原本「中模一框固定 30 個」的測試改成新的規則）：
  - 規格沿用桿徑與製程設定、只覆寫自己的欄位；改桿徑預設值會反映到沒有覆寫的規格。
  - 建立規格產生 7 個品項與第 1 版 BOM，整組的 BOM 依上沖、中模、下沖。
  - 輸入錯誤與代碼重複被拒絕；兩個請求同時建立同一個代碼只會成功一個。
  - P30-HX10 × 120 組展開：一根 13／16／15 支、10／8／8 根、多 10／8／0 支，共 26 根。
  - 單一零件只展開那一種；備料不能展開。
  - Φ24 的中模一框 45 支、電鍍一爐 56 支。
- 用 HTTP 實際呼叫各端點確認：查詢 `kind` 原本只接受大寫開頭（和 JSON 的小寫不一致），已改成大小寫都接受、不認得的回 400。
- 共用契約已重新建置並複製到 Unity。

## 3. 第 2 步：庫存與採購（2026-10-22）

### 資料表

| 資料表 | 內容 |
| --- | --- |
| `StockBalances` | 一個品項在一個站點的庫存：在庫、已保留；可用＝在庫 − 已保留。(品項, 站點) 唯一 |
| `StockReservations` | 一筆保留：誰（例如工單號碼）占住多少、還剩多少；剩 0 就結束 |
| `StockMovements` | 異動帳（只新增）：初始、收貨、盤點、領用、切料產出，數量有正負，記下異動後的在庫 |
| `PurchaseOrders` | 採購單：只買圓棒，一張單一個品項；已訂購 → 已收貨／已取消 |

- 圓棒與備料都放原料倉（`raw-store`）。
- 安全庫存記在品項上，只有圓棒有設（示範 30 根）。
- 資料庫約束：在庫與保留不會是負數，保留不會比在庫多；保留的剩餘量在 0 與保留量之間。

### 規則

- **保留**：最多保留需要的量，可用的不夠就保留可用的全部（不等料，有多少先用多少）。領用時在庫與保留一起扣；取消保留時只扣保留。這一層先寫好給第 4 步的工單用。
- **兩邊同時改同一筆庫存**：庫存列用 PostgreSQL 的 xmin 做樂觀並行控制。後存的那一邊會失敗，系統重新讀取再做一次（最多 3 次），所以保留的總數不會超過在庫。
- **安全庫存提醒**：可用量低於安全庫存就提醒，系統不會自己下採購單。訂了還沒到的不算可用，但會扣在建議量裡：建議量＝安全庫存 − 可用 − 已訂購（最少 0）。
- **採購單**：由人建立，收貨時才入庫。收貨會在同一筆交易裡把採購單改成已收貨、圓棒入庫、記一筆收貨異動；同一張單被收兩次（或兩個人同時按）只有一次成功，另一次回 409。已收貨或已取消的單不能再收貨或取消。
- **重送不會多一張**：建立採購單時可以帶 `Idempotency-Key` 標頭。同一個鍵重送回傳原本那張單（200）；同一個鍵但內容不同回 409；兩個同鍵的請求同時到，由唯一索引擋下後到的那一個。
- **盤點調整**：數量可正可負，不能調到比已保留的還少；只有圓棒與備料可以調。
- **示範重設**（`POST /api/demo/reset`）也會清掉庫存、保留、異動與採購單，再放回初始庫存。

### API

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| GET | `/api/inventory` | 每個品項的在庫、已保留、可用、安全庫存、已訂購，以及提醒 |
| GET | `/api/inventory/alerts` | 只看提醒 |
| GET | `/api/inventory/movements?itemCode=&take=` | 異動帳，新的在前 |
| POST | `/api/inventory/adjustments` | 盤點調整 |
| GET | `/api/purchase-orders?status=ordered` | 採購單 |
| POST | `/api/purchase-orders` | 建立採購單（可帶 `Idempotency-Key`） |
| POST | `/api/purchase-orders/{id}/receive`、`/cancel` | 收貨入庫、取消 |

錯誤的格式和規格的端點一樣：輸入錯誤 400、找不到 404、和目前狀態衝突 409（共用 `ApiErrorFilter`）。

### 示範值與 Claude 自己決定的部分

- 初始庫存：圓棒 40 根、P30-RD12 三種備料各 40 支；安全庫存 30 根。挑這個數量是為了讓一般的單切完會低於安全庫存，下 300 組時圓棒不夠。
- 提醒用「可用量」判斷（不是在庫量），訂了還沒到的不算可用。
- 收貨時整張單一次入庫，沒有部分收貨。
- 採購單先由人按收貨；依交期自動到貨，留到第 6 步調整時間時再做。

### 驗證

- 自動測試 121 個（新增 8 個）：
  - 初始庫存與安全庫存；要保留的比可用多時只保留可用的，並出現提醒、不會自動下單。
  - 兩個保留同時進來（各要 30、在庫 40）：一邊拿到 30、另一邊重試後拿到 10。
  - 領用與取消保留後的在庫、保留與異動帳。
  - 盤點不能調到比已保留的少；整組不能盤點。
  - 採購單：已訂購的量扣在建議量裡；兩個人同時收貨只入庫一次；收貨後不能取消；只能買圓棒。
  - 同一個 Idempotency-Key 同時送兩次只會有一張單，內容不同時回 409。
- 測試用的 PostgreSQL 容器把連線上限從 100 調到 500：每個測試各有一個資料庫與連線池，新增的測試讓整個集合超過預設上限（只影響測試）。
- 用 HTTP 實際呼叫：建立採購單 201、同鍵重送 200、收貨 200、再收一次 409、盤點、異動帳、示範重設後庫存回到初始值。
- 共用契約已重新建置並複製到 Unity。

## 4. 第 3 步：切料站（2026-10-22）

### 位置

原料倉所在的下排已經從西牆排到東牆，旁邊沒有空位。問過使用者，選擇把廠房往西加寬 8 m，切料站排在原料倉左邊（下排 X = -28）。

- 地面從 52 × 30.4 m 變成 60 × 30.4 m，西牆移到 X = -34，工廠大門仍在西牆中間。
- 內外兩條車道一起往西延長：外圈 X 從 -30 到 22、內圈從 -28.2 到 20.2，車道間距不變；新增的節點與連接路段在後端 `DemoRoadNetwork`，Unity 的 `FactoryLayout` 用同樣的數值畫。
- 場地中心不在原點了：Unity 的預設視角改看 X = -4，距離從 50 m 拉到 56 m，整個廠房仍在畫面內。
- 舊資料庫啟動時，路網會自動補上新的節點與路段（和以前一樣）。

### 流程

- 切料是第 0 道工序（`IsCutting`），每支 5 分鐘（使用者確認）。只有要從圓棒切的框會經過；用現成備料的框直接從粗加工開始。
- **建立批次**（`POST /api/lots` 多了 `specCode`；沒給就用該桿徑的示範規格 P30-RD12／P24-SQ08）：
  1. 每種零件先保留並領用原料倉現成的備料，裝成直接送粗加工的框。
  2. 不夠的從圓棒切：圓棒根數＝要切的支數 ÷ 一根切幾支（無條件進位），整根切完，多出來的算在最後一框。
  3. 圓棒依累計支數分到各框：第 k 框用到第 ⌈前 k 框的支數合計 ÷ 一根切幾支⌉ 根為止。跨兩框的那一根算在前一框；這是帳上的分配，總根數與總支數是對的。
  4. 依框的順序保留圓棒。保留到夠的框送去切料站；不夠的框留在原料倉「等料」（新狀態 `AwaitingMaterial`），沒有搬運任務。
- **等料的框**：生產背景工作每一輪依建立順序再保留一次。採購單收貨或盤點補進圓棒後，下一輪就接上，送去切料。
- **切完一框**：領用這一框保留的圓棒，多出來的備料記成「切料產出」放回原料倉，框送往粗加工。多出來的備料直接算入庫，沒有另外派車搬回原料倉。
- **補做的料**：有規格的框報廢時，補做的框先在原料倉等料，下一輪分配：現成的備料夠整框就直接送粗加工，否則排切料、保留圓棒。補做不再憑空出現料。
- 切料站的待加工與完工容量都是 30（比照車床），一次切一框。
- 新的資料表 `CuttingJobs`：每一框的備料品項、一根切幾支、要用幾根、已保留幾根、要切幾支、多出幾支、完成時間。

### Unity 與模型

- Blender 模型 `Station_Cutting`：臥式帶鋸機（橘色鋸弓）、右側滾筒進料台上一根圓棒、左側出料滑槽、後方圓棒架；機邊兩個台子和車床同一個位置，右邊放待切的圓棒、左邊放切好的備料，有料時才顯示。
- `FactoryLayout` 的地面與車道改成矩形（西側比東側長），`FactorySceneBuilder` 依矩形畫牆、柱子與走道；已重建 `Factory.unity`。

### 示範值與 Claude 自己決定的部分

- 切料站放在原料倉左邊、廠房往西加寬：使用者選的；加寬的寬度 8 m（剛好一個站位）是 Claude 定的。
- 切料的測試倍率 80、待加工與完工容量 30，比照車床，是 Claude 挑的。
- 現成備料和新切的備料分開裝框（例如 120 支、現成 40 支：30、10 兩框現成，30、30、20 三框新切），不混在同一框。
- 多出來的備料直接入庫，不另外派車；之後要畫成搬運再說。
- 一框的圓棒保留不夠時先留著已保留的部分，等補齊再一起送去切，不會切一半。

### 驗證

- 自動測試 126 個（新增 5 個）：
  - 120 支、現成 40 支：現成的裝成兩框送粗加工，80 支從圓棒切（7 根、多 11 支），三框分到 3、2、2 根。
  - 切完一框：用掉 2 根圓棒、切 26 支、多 6 支入庫，框送往粗加工；異動帳記下領用與切料產出。
  - 圓棒只剩 4 根時：第 1 框備齊、第 2 框保留 1 根、其他等料；採購 5 根收貨後，下一輪第 2、3 框備齊、第 4 框保留 2 根。
  - 補做：有現成備料的直接送粗加工，沒有的排切料（1 根、切 13 支、多 12 支）。
  - 規格不存在或和桿徑不合是輸入錯誤；沒指定規格時用示範規格。

## 5. 第 4 步：客戶訂單與生產工單（2026-10-22）

### 資料表

| 資料表 | 內容 |
| --- | --- |
| `SalesOrders`、`SalesOrderLines` | 客戶訂單：客戶、交期（可不填，只是記錄）、建立時的 Idempotency-Key；明細是品項（整組或單一零件）與數量 |
| `ProductionOrders` | 生產工單：主工單或補做工單、屬於哪一行明細、補做工單連回哪一張主工單、品項、數量、BOM 版本，以及開立時解析好的規格（`Spec_` 開頭的欄位） |
| `ScrapRecords` | 報廢註記：在哪一張工單、哪一框報廢了幾支，記在主工單上，連到因此開立的補做工單；同一框的同一次檢驗只會有一筆 |
| `Lots` | 多了 `ProductionOrderId`：框屬於哪一張工單（補做的框屬於補做工單） |

### 規則

- **一行明細一張主工單**。工單號碼沿用訂單號碼：訂單 `SO-20261022-012074` 的第 1 行是 `WO-20261022-012074-1`。
- **開立工單時在原料倉建立它的框**：和第 3 步一樣，先用現成的備料，不夠的從圓棒切，圓棒不夠的框先等料。框的批次編號就是工單號碼。訂單、明細、工單、框、庫存保留與搬運任務在同一筆交易寫入。
- **規格快照**：工單開立時把解析好的規格存下來（桿徑、一框幾支、中模外徑、三種備料長度、加工秒數的覆寫值），也記下品項目前的 BOM 版本。之後改規格或桿徑，已開立的工單不受影響：
  - 切料（含之後的補做）用工單存下的備料長度。
  - 粗加工、精加工的每件時間：規格有覆寫就用工單存下的覆寫值（例如六角 10 的精加工 90 秒）；沒有覆寫的沿用製程設定的現值，面板改了會跟著變。
- **重送不會多一張**：建立訂單可以帶 `Idempotency-Key`。同一個鍵重送回傳原本那張訂單（200），不會多開工單、多建框、多用備料；同一個鍵但內容不同回 409；兩個同鍵的請求同時到，由唯一索引擋下後到的那一個，它重來時會找到先建立的那一張。
- **報廢與補做**（使用者確認）：有工單的框在品管報廢時，在主工單上記一筆報廢註記，另開一張補做工單（主工單號碼加 `-R1`、`-R2`…），補做的框屬於補做工單。補做工單裡又報廢時，一樣記在主工單、再開一張，連回主工單（不是連回上一張補做）。補做工單的規格沿用主工單開立時存下的那一份。
- **補做的框的批次編號仍是主工單的號碼**，所以同一張主工單的料（含補做）照第 4 步以前的規則一起裝箱、一起出貨；出貨改看整張訂單是第 5 步。
- **進度**：每一行明細、每種零件：訂購、完成（包裝完成）、製作中（等料、在原料倉、在車上、在各站）、報廢、補做。主工單與補做工單合計；每一行的每種零件都完成，訂單就完成。
- **面板的「建立批次」改成下一張客戶訂單**（客戶是「面板下單」）：三種零件都做就是一行整組，只做其中幾種就每種零件一行。API 與回應的格式不變，Unity 面板不用改。

### API

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| POST | `/api/sales-orders` | 建立客戶訂單（可帶 `Idempotency-Key`；400 輸入錯誤、409 同鍵不同內容） |
| GET | `/api/sales-orders`、`/api/sales-orders/{id}` | 訂單、每一行的進度、工單與報廢註記 |
| GET | `/api/production-orders`、`/api/production-orders/{id}` | 工單（含補做）、開立時的規格、進度；查單一工單時含它的框 |
| POST | `/api/lots` | 面板的「建立批次」：下一張客戶訂單，回應是建立的每一框 |

輸入限制：客戶名稱必填（最多 64 字）；交期不能早於今天；1～20 行；品項只能是整組或單一零件（不分大小寫）；每行 1～300 組或支。

### 示範值與 Claude 自己決定的部分

- 訂單、工單的號碼格式。
- 交期放在訂單上（整張訂單一起出貨，所以不放在每一行）。
- 沒有覆寫的加工秒數不存進工單，沿用製程設定的現值（面板是示範用的調速工具，改了應該馬上看得到）。
- 補做工單的 BOM 用那個零件建立補做工單時的最新版本；規格沿用主工單的快照。
- 完成以「包裝完成」計算（包好的框、併進出貨箱的框）。
- 一張訂單最多 20 行。
- 現在還沒有取消訂單、修改訂單。
