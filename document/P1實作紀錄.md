## 2. 實作時做出的技術決定（Claude，可調整）

以下是讓 P1 可以跑起來的技術選擇，不是業務規則。若與你的想法不同，都可以改。

| 項目 | 目前做法 | 理由 |
| --- | --- | --- |
| 套件版本 | MQTTnet 5.2.0、Mosquitto 2（實測 2.1.2）、xUnit 2.9 | 撰寫時的最新穩定版；MQTTnet 5 已移除 ManagedClient，因此自行實作重連 |
| 契約專案 | `OpenFleet.Contracts` 以 netstandard2.1、C# 9 撰寫，不依賴序列化套件 | Unity 6 可直接引用同一份契約；Unity 端可改用 Newtonsoft，只要設定 camelCase 與字串 enum |
| JSON 規則 | camelCase 欄位；enum 以小寫字串表示（例如 `completed`） | 可讀性高，版本演進時比數字 enum 安全 |
| 車輛 ID | 使用字串代碼 `agv-01`～`agv-03` | P1 沒有資料庫；P2 建立資料表時再決定 UUID 與代碼的關係 |
| FactoryId | `demo` | 單一工廠示範 |
| 狀態 Topic | `state/vehicles/{id}` 使用 retained | 顯示端一訂閱就能拿到最新狀態 |
| MQTT Session | CleanSession，每次重連都重新訂閱 | 行為單純；斷線期間的訊息由 HTTP 快照補齊 |
| 狀態保存 | 只存在記憶體 | P1 只驗證通訊；P2 導入資料庫 |
| 去重 | 事件用 `(producerId, messageId)` 去重；遙測用 `sessionId + sequence` 丟棄舊資料 | 對應文件第 7 節的規則 |
| 驗證指令 | 新增 `Ping` 指令，模擬器回報 `accepted` → `completed` | P1 還沒有搬運任務，需要一個不影響業務狀態的往返指令 |
| 模擬器移動 | 2026-09-27 起沿環狀主走道（`Simulator:Route`）循環行駛，速度 1 m/s，各車平均錯開（原本是每台車繞半徑 5 m 的圓） | 只用來產生位置變化，不代表路網、派工或交通模擬 |

## 3. 暫用的示範設定（需要你確認）

文件原本寫「心跳、離線與逾時的秒數需要依展示／真實設備情境設定」。為了讓 P1 可以驗證，先填入下列示範值，**尚未定案**：

| 設定 | 示範值 | 位置 |
| --- | --- | --- |
| 遙測頻率 | 每秒 5 次（200 ms） | `Simulator:TelemetryInterval` |
| 判定離線 | 3 秒沒有任何回報 | `Fleet:OfflineAfter` |
| 離線檢查間隔 | 1 秒 | `Fleet:LivenessCheckInterval` |
| 指令有效期限 | 10 秒，逾期時設備回報 `rejected` | `Fleet:CommandTimeToLive` |
| MQTT 重連間隔 | 2 秒（固定間隔，沒有指數退避） | `Mqtt:ReconnectDelay` |

## 4. 驗證結果（2026-09-26）

- 自動化測試：18 個全部通過，連續跑 6 次都穩定。端對端測試使用程式內嵌的 MQTTnet broker，不需要 Docker。
- 手動驗證（真正的 Mosquitto）：
  - 指令往返成功，`mosquitto_sub` 收到 retained 狀態 JSON。
  - `docker restart` Broker 後，後端與模擬器都自動重連，重連後 Ping 依然成功。
  - 停止模擬器 3 秒後，兩台車都轉為 `offline`。重啟模擬器後出現新的 Session，車輛恢復為 `online`。

### 發現的限制

後端使用的 MQTTnet 5（5.2.0）只提供 net8.0／net10.0 版本，Unity 6 不能使用。這不影響後端：MQTT 是標準協定，Unity 端可以用其他 client 連到同一個 Mosquitto。

### 使用者決定（2026-09-27）

| 項目 | 決定 |
| --- | --- |
| Unity 端 MQTT client | MQTTnet 4.3.7（含 ManagedClient） |
| 第一個驗證平台 | Windows 桌面版 |

### 當時的選項

1. **Unity 端 MQTT client**
   - A. MQTTnet 4.3.7（有 netstandard2.1 版本）。Claude 建議選這個，因為 API 與後端相近，也支援 async/await。
   - B. M2MqttUnity。它專為 Unity 設計，但已久未更新，與 Unity 6、IL2CPP 的相容性需要自行驗證。
2. **Unity 端第一個驗證平台**：Windows 桌面版或 WebGL。WebGL 只能透過 WebSocket（Mosquitto 的 9001 埠）連線，需要另外處理。

### Unity 端 P1 的原定步驟（已完成，見第 7 節）

1. 加入所選的 MQTT client，以及共用契約 `OpenFleet.Contracts` 和 JSON 設定（camelCase、字串 enum）。
2. 訂閱 `state/vehicles/+`，把收到的訊息透過佇列切回主執行緒，更新場景中的車輛位置與狀態顏色。
3. 驗證 Broker 重啟後能自動重連；用 HTTP 快照加上 `version` 欄位對齊狀態。

## 7. Unity 端實作與驗證（2026-09-27）

### 實作時做出的技術決定（Claude，可調整）

| 項目 | 目前做法 | 理由 |
| --- | --- | --- |
| 套件放置 | MQTTnet 4.3.7、ManagedClient 4.3.7 的 netstandard2.1 DLL 直接放在 `Assets/OpenFleet/Plugins` | 兩者在 netstandard2.1 沒有其他相依套件；不需要額外的 NuGet 匯入工具 |
| 共用契約 | 建置 `OpenFleet.Contracts.dll` 複製到 Unity，用 `unity/sync-contracts.ps1` 同步 | 直接引用原始碼資料夾會把 `bin/obj` 一起匯入並在 backend 產生 `.meta` |
| JSON | Unity 官方的 Newtonsoft 套件 3.2.1 | 設定 camelCase、enum 小寫字串，與後端一致 |
| 重連 | ManagedMqttClient，每 2 秒重試，重連後自動重新訂閱 | 與後端 `Mqtt:ReconnectDelay` 相同 |
| ClientId | `openfleet-unity-{隨機值}` | 同時開多個 Editor／Player 時不會互相踢線 |
| 主執行緒 | `ConcurrentQueue<Action>`，在 `Update` 取出執行 | 背景執行緒只做 JSON 解析，不碰 Unity 物件 |
| 對齊 | 每次連上 Broker 都取一次 HTTP 快照；以 `stateEpoch` + `version` 丟棄舊狀態 | 見下方「發現的問題」 |
| 顯示 | 最初用方塊代表 AGV，綠色 online、灰色 offline；位置指數平滑插值；IMGUI 面板可送 Ping。2026-09-27 起改為工廠場景與車型模型（第 10 節） | P1 只驗證通訊 |

### 發現的問題與修正：後端重啟後 Unity 停止更新

`version` 只存在後端記憶體，後端重啟後從 0 重新計算。Unity 原本只比 `version` 大小，會把重啟後的新狀態當成舊資料全部丟掉（實測 Unity 停在 v1108，後端已經是 v55）。

修正：`VehicleState` 新增 `stateEpoch`（Guid，後端每次啟動產生新值）。epoch 相同才比較 version，不同就直接採用。後端新增 1 個單元測試，共 19 個測試通過。這是契約的新增欄位，舊的接收端會忽略它，所以沒有提高 `schemaVersion`。

### 驗證結果（Windows Player，Development build）

| 情境 | 結果 |
| --- | --- |
| 啟動 | 連上 Broker、收到 retained 狀態、載入 HTTP 快照，兩台車顯示為綠色並繞圈移動 |
| Ping | `POST /api/vehicles/{id}/ping` 後，Unity 收到 `completed` |
| Broker 重啟（`docker restart`） | Unity 記錄 disconnected → connected，重新取快照；重連後 Ping 正常 |
| 模擬器停止 | 約 3 秒後兩台車轉為 offline（灰色） |
| 後端重啟 | 修正後，Unity 偵測到 epoch 變更並採用新狀態 |

補充：Editor 不在前景時，Play Mode 幾乎不會更新畫面（實測只跑了 2 個 frame）。這是 Editor 的行為，不是程式的問題。因此改用 build 出來的 Player 驗證。
