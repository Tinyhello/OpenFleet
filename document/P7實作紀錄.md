# P7 實作紀錄：沙盒佈局

## 1. 範圍與步驟

P7 讓工廠的佈局可以由使用者自己擺：機台、AGV 與 AGV 的路線都模組化，可以依需求增減數量、決定實際擺放的位置，類似沙盒模式。使用者 2026-10-24 決定的規則：

- **每台機台一個模組**：每台車床、每座爐、每個工站都獨立擺放，各有自己的 AGV 交接點與備料區、成品區（車床備料區 30 支，是先前確認過的數值）。AGV 送料時才決定送到同一道工序的哪一台。P6「兩台車床共用一個交接點與備料區」的做法改掉。
- **AGV 路線也由使用者拖曳擺放**；車道不限方向（沿用先前的決定）。
- **工廠清空時才套用**：編輯時工廠照常運轉；按「套用」時如果還有訂單在做，提示可以「清空示範資料並套用」；套用後 AGV 回到各自的車位重新開始。
- 一併要做：**廠房大小可調**、**多份佈局存檔**（另存、載入，並且一定能回到預設佈局）、**裝飾物也能擺放**（雜物倉庫、載具存放區）。
- 不做：一次畫兩條平行車道的畫法、生產中即時改佈局。

實作分成幾步，每一步做完先給使用者看：

## 2. 設計重點

- **佈局**是一份文件：廠房大小、模組（種類、位置、朝向）、路網（節點與路段）。可以存很多份，同時只有一份使用中。
- **模組**分四類：機台（每台一個工站，同一道工序可以放好幾台）；倉儲站（原料倉、成品倉、出貨、刀具庫）；AGV 車位（放一個車位就是多一台 AGV）；裝飾物。
- **套用**＝清空生產資料 → 由佈局推導出站點、機台、刀具、路網與車輛 → 重新載入路網、重置交通控制 → 發布新的佈局版本，模擬器依車輛清單增減車輛、所有車回到車位，Unity 依新佈局重建場景。
- 製程（工序、加工時間、測試倍率）不屬於佈局，仍在示範設定。佈局只決定每道工序有幾台、放在哪裡。
- 後端與 Unity 共用一個佈局程式庫（模組目錄、幾何、驗證、路網編輯、預設佈局），Unity 編輯時的即時檢查和後端套用前的檢查結果一致。
- **送料選哪一台**：
  - 逐件工序（切料、車床、拋光、品管、包裝）：在放得下的站裡，先看換線與批次（沿用 P6 的排名），再看機台能不能馬上做（沒有在等刀、換刀、成品台沒卡住），再看路程，最後看代碼。
  - 整爐工序（淬火、回火、電鍍）：先送到沒在跑、爐前已經有料的爐（料多的先，先湊滿一爐），其次是沒在跑的空爐，最後才是正在跑的爐。

## 3. 第 1a 步：工序與工站分開（2026-10-24）

### 資料表（Migration `SeparateStepsFromStations`）

- `ProcessSteps`：`StationCode` 改名為 `Code`（工序代碼，與原本的站點代碼相同：cutting、rough…），新增 `Name`（工序名稱，從工站的站名回填），`Code` 唯一。不再有到工站的外鍵。
- `Stations.StepSequence`：工站屬於哪一道工序（倉儲站與出貨站是 null）。
- `TransportTasks`：`ToStationCode` 可為空；新增 `ToStepSequence`。檢查條件：目的站與目的工序至少要有一個。送到工序的搬運在待派工時目的站是空的，派車時才定（`BindDestination`）。
- 舊資料不用搬：工序代碼就是原本的站點代碼，舊的加工紀錄、搬運與機台都照原樣接得上。

### 規則

- **搬到某道工序的框**：建立搬運時只記工序（`TransportTask.CreateToStep`）。派車時（`TransportService.DispatchPendingAsync`）：
  1. 目的站放不下的不算，都放不下就繼續等，不占用車輛，也不算缺車。
  2. 有車可派才選站。只有一站就是那一站；有好幾站時由 `StationSelector` 挑：逐件工序依換線排名（站上機台最好的那一台）→ 機台馬上能做的 → 路程 → 站代碼；整爐工序依爐前有沒有料（料多的先，先湊滿一爐）→ 沒在跑的 → 正在跑的（爐前料少的先）→ 路程 → 站代碼。
  3. 選定後和派工在同一筆交易寫入。
- 送到工序的搬運被退回（車拒絕、還沒取料就失敗）時目的站清掉，下次派車重新選。
- **整爐工序**：每座爐各自排隊與開爐（`StartBatchRunsAsync`）。「還會有料來」只算工序在這道工序之前的，或這道工序還在搬運中、還沒定站、或定的就是這座爐的；已經排在別座爐前或爐裡的不算。
- **預估**（`ScheduleForecaster`）：同一道工序的站共用排隊區；已經排在某座站前的框只能由那座站接；整爐每座爐各自算開爐；搬運時間用離來源最近的站。
- **缺車統計**（`VehicleShortageService`）：等不到料以工序為單位，同一道工序所有站的閒置機台、排隊與在送的框一起算。

### API 與 Unity 的契約

- `ProcessStepDto`：`StationCode`／`StationName` 改為 `Code`／`Name`（設定頁的工序清單）。
- `StepDelayDto`：`StepCode`／`StepName`（缺車統計的工序）。規格兩處寫法不同，這裡採用工序的命名（見第 5 節）。
- `TransportTaskDto`、`VehicleWaitDto`：`ToStationCode` 可為空，新增 `ToStepName`（待派工時顯示工序名稱）。
- `StationDto`、`StationStatusDto`：新增 `StepSequence`。
- `MachineScheduleDto`：新增 `StepSequence`（面板依製程順序排機台；原本用站代碼推工序，之後一道工序多站時會錯）。
- Unity：`ProductionPanel` 改用新欄位；待派工的搬運顯示工序名稱；排程的機台排序改用 `StepSequence`。契約 DLL 已用 `unity/sync-contracts.ps1` 同步。Unity 檔案是 CRLF，改動時保留原本的換行。

| --- | --- |
| `FactoryLayouts`（新） | `Id`、`Name`（40 字，唯一）、`Document`（jsonb，和 MQTT、HTTP 共用 `JsonDefaults`）、`IsDefault`、`IsActive`（部分唯一索引）、`CreatedAt`、`UpdatedAt`、`AppliedAt`、`AppliedHash`（文件 JSON 的 SHA-256） |

### 規則

- **結構檢查**（`LayoutValidator` 的第一步，問題代碼 `document-invalid`，錯誤）：文件來自 JSON，欄位可以是 null、種類可以是任意整數（`JsonStringEnumConverter` 允許整數），後面的檢查都假設結構完整，所以先擋。檢查項目：文件、`Floor`、`Modules`／`RoadNodes`／`RoadEdges` 為 null；清單裡有 null 的項目；模組或節點的代碼為 null 或空白；模組種類不是定義過的 `ModuleKind`（`Enum.IsDefined`）；路段的 From／To 為 null。有任何結構錯誤就直接回傳（`IsValid = false`），不跑後面的檢查；驗證器在任何輸入下都不丟例外。同一種問題只回一則，列出前 5 個項目的編號（從 1 起），多的用「…（共 N 項）」帶過。只有 null 算結構錯誤，空字串的路段端點照舊是 `edge-invalid`。
- **存檔**（`CreateAsync`、`UpdateAsync`）：在碰資料庫之前先驗證，有 `document-invalid` 就丟 `RequestValidationException("document", 訊息)`（400），不寫入；其他錯誤（重疊、缺工序…）照規格仍然可以存，沙盒常存半成品。驗證結果直接用在存檔後的回應，不再驗第二次。套用與 `/validate` 走驗證器：結構錯誤＝無效佈局，套用回 400，`/validate` 回 200 加問題清單（body 是 `null` 也一樣）。
- **推導**（`LayoutDeriver`，純計算）：工站與倉儲站各一筆；逐件工序的站各一台機台（代碼＝站代碼、編號 1、名稱＝站名）；有刀具的機台各一筆刀具狀態；路網照抄；每個 AGV 車位一台車（`InLayout`、派工）。整爐工序（淬火、回火、電鍍）的爐不是機台。
- **寫入**（`LayoutWriter`）：有的更新、沒有的新增、不在佈局裡的站與機台刪掉。車輛不刪，不在佈局裡的只退出派工（`InLayout = false`、`DispatchEnabled = false`）。路網整份換掉。
- **套用**（`LayoutService.ApplyAsync`）：
  1. 驗證，有錯誤回 400（`LayoutValidationDto`）。
  2. 暫停背景工作（`LayoutGate`），再檢查在製品。完成的框是 Scrapped、Boxed、Shipped，以及在成品倉的 Staged；其他的框、Pending／Assigned／Executing 的搬運、還沒出爐的爐都算在製品。有在製品且 `resetDemo=false` → 回 409（`LayoutBusyDto`）。
  3. 一筆交易：清空生產資料（`DemoData.ClearProductionAsync`，示範重設與套用共用）→ 清 `MachineDelays`、`VehicleWaits` → 寫入推導結果 → 初始庫存 → 這份佈局設成使用中（其他的關掉）→ 記下 `AppliedAt`、`AppliedHash`。
  4. 交易提交後從資料庫重新載入記憶體（`LayoutRuntime`）：路網、交通控制（`Reset`）、使用中的佈局（`ActiveLayout`）、退出佈局的車（`FleetStateStore.SetLayoutVehicles`）。
  5. `LayoutPublisher` 發布新的佈局版本（retained）；不在佈局裡的車清掉它們在 Broker 上的舊狀態（retained 的空訊息）。
- **啟動**（`InitializeDatabaseAsync`）：Migrate → `SeedAsync(db, DefaultLayout.Build())`（預設佈局每次用程式的文件覆寫；沒有使用中的佈局就讓它使用中並推導）→ 使用中的佈局驗證失敗，就改用預設佈局；預設佈局的雜湊和程式不同（程式改了），就重新套用；有在製品時只記錄警告。自訂佈局的文件改過但還沒套用，只記錄警告，不替使用者套用。最後從資料庫載入記憶體。
- **閘門**（`LayoutGate`）：生產、派工、交通三個背景工作每一輪開頭 `TryEnter`、結束 `Exit`；套用時 `PauseAsync` 擋住新的一輪、等進行中的一輪結束。MQTT 事件處理不擋（規格：晚到的事件找不到派工，本來就會被忽略）。
- **模擬器**：收到佈局版本後，新版本（`LayoutId` 或 `AppliedAt` 不同）換新的 `SessionId`，清掉舊的回報與待送事件，每台車放回車位、清掉工作與載貨；同一版本（重新連線時收到的 retained）只增減車輛，不動位置。不在清單裡的車，它的放行與指令一律忽略。例外：啟動後的第一個佈局，設定檔初始清單裡已經存在的車保留原位（仍然換 Session、清掉工作與路徑）；正式執行時初始清單是空的，所以不影響。

### Claude 自己決定的部分（待使用者確認）

1. 套用時先暫停閘門，再檢查在製品（規格的順序是先檢查再暫停）。先檢查的話，檢查與清空之間可能有新的訂單或搬運冒出來。
2. `LayoutGate.PauseAsync` 被取消時會恢復（規格沒寫）。否則取消後背景工作會永久停住。
3. 在製品的判斷：Staged 只有在成品倉才算完成（規格原文）；`BatchRuns` 還沒出爐也算在製品（規格沒列，但爐裡的料仍在流程中）。
4. 啟動檢查：預設佈局的雜湊不同才重新套用；自訂佈局只記錄警告，不自動套用（避免替使用者套用還沒按的修改）。
5. 部分唯一索引：`IsDefault` 也加一份（規格只寫 `IsActive`）。
6. `resetDemo` 查詢參數可以省略（最小 API 會把非可為 null 的 bool 當成必填）。
7. 路網寫入用 `ExecuteDelete` 加分離追蹤：同一個 `DbContext` 連續寫兩次時，追蹤會和新的節點衝突。
8. `LayoutGeometry` 的座標取到 9 位小數：避免 `-3.1999999999999997` 這類誤差，讓站點交接點和路網代碼對不上。
9. 模擬器換新版本時，清掉還沒送出的回報與事件（舊 Session 的，後端會當作重啟忽略）。
10. 交通控制找不到站點節點時先不動車（保守，不替它規劃路徑）。
11. 測試的車號（`agv-a`…）不符合代碼規則，只在測試資料庫裡存在；端到端測試用正式代碼（`agv-01`、`agv-02`）。
12. 結構錯誤的文件一律回 400、不寫入資料庫（規格沒寫）：文件或 `Floor` 為 null、三個清單為 null、清單有 null 項目、模組或節點代碼為 null 或空白、種類不是定義過的值、路段端點為 null。這些在寫入前由 `LayoutValidator` 的 `document-invalid` 擋下來（取代原本只檢查整份文件為 null 的 `RequireDocument`）。其他錯誤（重疊、缺工序…）仍然可以存，照規格沙盒常存半成品。沒有帶 `document` 欄位時，DTO 的預設值是空的文件（結構完整），照規格當成「有錯誤的佈局」存下來。
13. 端到端測試 `Lot_travels_from_raw_store_…` 原本假設同一批的第一框送到 1 號機。兩台車床都空著時，先派出去的框拿到較近的 1 號機，而同一批的框建立時間相同，派工排序靠 `Id`（隨機），所以可能送到 2 號機（單獨跑三次中失敗一次）。測試改成比對工序種類（粗加工、精加工）與搬運順序，不比對是哪一台同類機台；派工的排序沒有改。
14. 模擬器啟動後收到的第一個佈局，設定檔初始清單裡已經存在的車保留原位，不放回車位（仍然換新的 Session、清掉工作與路徑）；之後的新版本一律放回車位。理由：正式執行時初始清單是空的，不受影響；測試與離線用的初始清單可以指定起點，端到端測試才能讓車從離車位很遠的地方出發，驗證交通控制把閒置的車引導回車位（改成由佈局決定車輛之後，這個測試曾經因為車一開始就在車位上而什麼都沒驗到）。保留的是車目前的位置，而不是設定的起點：放行可能在佈局訊息之前就到了、車已經開出去一小段，這時不能把車瞬間搬走。

### 已知限制

- 閘門只擋背景工作。套用時如果有 HTTP 請求同時寫入（例如下單），理論上會有競態。目前是單機單人使用，示範資料可以接受；多人同時用時要再加鎖。
- Unity 場景還是 Editor 產生的，第 3 步才會依佈局建場景。套用非預設佈局之後，Unity 畫面和後端會不一致。（第 3 步已解除，見第 7 節。）

### 已知限制

- **後端問題（第 2 步，這一步沒改）**：套用佈局時被拿掉的車，它的 state Topic 先被清成空的 retained 訊息，之後又有一則非空的狀態被發布，所以 Broker 上留著那台車的舊狀態。實驗（套用拿掉 `agv-05` 的佈局，用 `mosquitto_sub` 看那個 Topic）：版本 29 之後是空訊息，再來又是一筆版本 30，發布時間在套用後 0.35 秒；另一次實驗查到的留存狀態，發布時間在套用後約 7 秒。後端的 `FleetStateStore.Retire` 已經忽略它的遙測，所以這筆是怎麼來的沒有查。Unity 現在靠車輛清單丟掉它；但別的訂閱者（或沒有這層保護的舊版 Unity）會看到一台已經被拿掉的車。可能的修法：`VehicleStatePublisher` 發布前檢查車是否還在 `FleetStateStore`、不在就不發。需要的話請告訴我是否要在後端處理。（使用者 2026-10-25 要求照這個修法處理，已修正，見第 10 節。）
- **套用後車輛回車位的過程**：量過 6 次套用（都在車輛正在跑的時候套用）：2 次後端在 0.5～2 秒內就把車放回車位（後端每 0.5 秒檢查一次要不要發布新版本，加上套用與模擬器處理的時間）；另外 4 次，車輛在套用後的數秒內（最久約 6 秒）仍在路網上移動，最後才停回各自的車位。後端 `/api/vehicles` 的位置也是這樣，所以不是畫面的延遲。其中一次還看到車開到別台車的車位支線上、甚至離開道路的座標（agv-04 在 agv-05 的車位支線上），我推測是套用前後端發出的舊放行路徑在套用後才送到模擬器，這只是推測，沒有查證（模擬器與交通控制的行為，第 6 步的長時間運轉驗收時一起看）。
- 路面畫法和第 1b 步不同（見上）；走道一側的視角沒有另外截圖（不能在使用者的螢幕上操作滑鼠與鍵盤；結構比對已涵蓋位置與尺寸）。
- 操作面板在後端還沒起來時只讀一次設定，之後不會重試：後端晚啟動時，面板的規格選單停在「（讀取中）」、設定頁顯示「讀取設定失敗」，要重開 Unity 才會好（第 3 步之前就有，這一步沒改）。
- 編輯模式、面板的「佈局」頁、`LayoutClient` 的實際使用都在第 4 步；這一步只有 HTTP 呼叫與場景重建。
- 進度條對視角很敏感（第 1b 步的已知限制）：預設視角下剛好不重疊，拉遠就會碰在一起。
- 左上狀態列（IMGUI，預設字型）的中文「等待後端佈局…」看起來像有一條刪除線（截圖放大可見），應該是預設字型沒有中文、改用系統字型的效果；同一列原本只有英文。之後改成用有中文的字型，或改用面板顯示。

## 8. 第 4 步（上）：共用程式庫的佈局編輯（2026-10-25）

第 4 步的純計算部分：路網編輯、模組代碼、編輯模型，都在 `OpenFleet.Layout`（netstandard2.1，Unity 與後端共用），有單元測試。Unity 的編輯器（面板、滑鼠鍵盤、場景重畫）還沒開始。

### 規則

- **路網編輯 `RoadGraphEditor`**：座標四捨五入到 0.01 m；節點代碼 `NodeCode(x, z)`（最多兩位小數、invariant、`-0` 寫成 `0`），`DefaultLayout.Code` 改用它，預設佈局每個節點的代碼不變。常數在 `LayoutRules`：`MergeDistance` 0.3、`MaxSegmentLength` 4、`MaxSpurLength` 8、`OnEdgeDistance` 0.01。
  - `EnsureNode`、`SplitEdge`、`AddRoad`（第 5 步用，這一步先做好並測試）、`MoveNode`、`DeleteNode`、`DeleteEdge`、`ConnectModule`、`DisconnectModule`、`ReconnectModule`、`RemoveModule`。
  - `ConnectModule`：從交接點沿朝向找 8 m 內第一條碰到的路段，連一條單一路段的支線（不切段）；8 m 內沒有路就不接，交接點節點留著（驗證會報 handoff-missing／unreachable）。**落點離既有節點太近的處理**（使用者 2026-10-25 決定，互動驗收發現，見第 9 節）：車道節點每 4 m 一個，落點常離節點不到 `MinEdgeLength`（1.6 m），在那裡切段會留下過短路段（實測 0.4 m，報 `edge-short`、`edge-clearance`）；所以落點離被碰到路段較近的端點不到 1.6 m 時，支線直接接到那個既有端點（不切段，支線略斜）；兩端都不到 1.6 m（路段短於 3.2 m）取較近的；其餘（離兩端都 1.6 m 以上）照舊在落點切段、支線垂直。`DisconnectModule` 的合併規則（兩段合起來不超過 4.01 m）不會把 4 m ＋ 4 m 的車道節點合掉，所以斜支線拆掉後路網回到原樣（有測試）。
  - `DisconnectModule`：刪交接點與支線；原本接上的路口只剩兩條路段、一直線（偏離 0.01 m 內）、合起來不超過 4.01 m、不是別的模組的交接點時合回一段；沒有路段的節點刪掉（別的模組的交接點除外）。
- **模組代碼 `ModuleCodes.Next(document, kind)`**：機台 `{工序代碼}-{n}`、AGV 車位 `agv-{nn}`（至少兩位數）、裝飾物 `misc-{n}`／`carrier-{n}`，取最小沒用過的正整數；倉儲站回傳固定代碼，已經有了就回傳 null。結果一定符合 `ModuleCatalog.IsValidCode`。
- **編輯模型 `LayoutEditSession`**：Unity 只做輸入與繪製，所有修改都經過它。
  - 對草稿（建構時複製的一份）新增、移動、旋轉、刪除模組，自動接路；位置對齊 0.2 m；廠房大小以目前中心縮放、對齊 0.4 m、限制在規則範圍、座標取到 0.01 m。
  - 復原／重做最多 50 步（使用者決定），失敗或沒改到東西的操作不留紀錄；連續的 `SetFloorSize`（拖滑桿）合成一步；`IsDirty` 與上次儲存（`MarkSaved`）的狀態比對，復原回到儲存時的狀態就不再是 true。
  - `CanAdd`（倉儲站已有、模組上限 120、AGV 車位上限 20 不行）、`CanRemove`（倉儲站不行）、`CanPlace`（占地在廠房內、不和別的模組重疊，貼邊可以；拖曳時的紅綠框線用）、`Validate`（共用的 `LayoutValidator`）。
  - 復原與重做會換掉草稿物件，操作後要重新讀 `Document`。
- 共用程式庫不能用 System.Text.Json，所以文件的深複製與比較用手寫的 `LayoutDocuments.Clone`、`LayoutDocuments.Canonical`（測試用屬性數量檢查提醒同步）。

1. **新增、移動不因重疊或超出廠房而拒絕**：照規劃「刻意做出錯誤 → 紅框與錯誤清單」；拖曳的紅綠由 `CanPlace` 提供，要不要在放開時擋掉由 Unity 這一側決定。
2. **`ConnectModule` 找不到路時，交接點節點照樣留在路網**（沒有路段）：規劃寫 `h＝EnsureNode(交接點)` 在前；之後再移動或拆掉這個模組時會一併清掉。
3. **`EnsureNode` 的 0.3 m 合併也適用於交接點**：交接點落在別的節點 0.3 m 內時會接到那個節點（座標可能和交接點差到 0.3 m，超過驗證的 0.05 m 比對時會報 handoff-missing）。照規劃字面實作；0.2 m 格點加上交接點偏移，平常不會碰到。
4. **`DisconnectModule` 不會刪掉別的模組的交接點**，即使它因此沒有路段（規劃寫「沒有路段的節點刪掉」；這裡和 `DeleteEdge` 一致，交接點除外）。
5. **共線的判斷**：路口到兩個鄰點連線的距離在 0.01 m 內（和 `EnsureNode` 切路段的容許值相同），所以切開再合回是對稱的。
6. **AGV 車位上限**取 `LayoutRules.MaxVehicles`（20）、模組總數上限取 `MaxModules`（120），`CanAdd` 就擋；不檢查路網節點上限（1500）。
7. **`AddRoad` 的交叉點**：只處理不平行的路段；平行重疊的部分靠「剛好在新路段上的既有節點」（0.01 m 內）串起來；既有節點離新路段超過 0.01 m 但在 0.3 m 內時不會自動併入。
8. **模組代碼的「已用」**以文件裡所有模組的代碼為準（不分種類）。
9. **`SetFloorSize` 不檢查模組是否還在廠房內**（驗證會報錯），也不檢查路網是否超出。

### 已知限制

- Unity 的編輯器（第 3 頁面板、滑鼠鍵盤、場景重畫、驗證清單、佈局存檔操作）還沒做，這一步只有計算層；`AddRoad` 要到第 5 步才有人用。
- 路段與節點的查找是線性搜尋（最多 1500 個節點）；拖曳中每次放開才算一次，沒有效能顧慮，之後若要每個 frame 呼叫再改成索引。
- 節點代碼不是座標格式的舊文件（手寫的代碼）在 `MoveNode` 改座標時會改成座標格式的代碼；代碼碰撞只靠「0.3 m 內合併」避免，沒有另外檢查。

### 操作方式（滑鼠與鍵盤）

- **滑鼠**：從攝影機射到 y = 0 的地面，用模組的占地矩形（`LayoutGeometry.Footprint`）判斷點到誰（重疊時取面積最小的），不靠物理碰撞體。左鍵按在模組上＝選取並開始拖曳（位置對齊 0.2 m，按下後要移動 4 個像素才算拖曳）；按在空地＝取消選取。右鍵與中鍵拖曳仍是攝影機。滑鼠在面板或左上狀態框上時不處理場景。正常模式下場景沒有任何左鍵行為，所以沒有衝突。
- **拖曳**：只移動那個模組的物件，框線與墊片依 `CanPlace(…, ignoreCode: 自己)` 變綠或紅；放開才 `MoveModule`、整個場景重畫、驗證。Esc 取消拖曳。
- **新增**：按面板按鈕 → 模組的複本（Ghost）跟著滑鼠（占地中心對準滑鼠、對齊 0.2 m），R 旋轉，左鍵放下（`AddModule`，放下後結束擺放並選取新模組），Esc 取消；框線綠或紅。
- **鍵盤**：R 旋轉（選取的模組或擺放中的）、Delete 刪除選取的模組（倉儲站不行）、Esc（取消拖曳 → 取消擺放 → 取消選取）、Ctrl+Z 復原、Ctrl+Y 或 Ctrl+Shift+Z 重做。原有的 WASD／F／Esc（攝影機）、Ctrl+＝／－／0（介面大小）不受影響；拖曳中 R、Delete、復原、重做都不處理。
- **面板「佈局」頁**，由上到下：確認區塊與訊息（平常隱藏）→ 進入編輯／離開編輯、復原、重做、佈局名稱與「＊未儲存」→ 新增模組（可收合；機台、倉儲、AGV、裝飾，每個按鈕帶目前數量，例如「粗加工車床（3）」，不能新增的停用，擺放中的反白）→ 選取的模組（名稱、代碼、位置、朝向、旋轉 90°、刪除）→ 廠房大小（寬 40～100 m、深 24～60 m 兩個滑桿，每格 0.4 m）→ 檢查結果（「N 個錯誤、M 個警告」與每一條，點一條選取第一個模組、沒有模組就看第一個節點，並用 `Focus` 把攝影機移過去）→ 佈局存檔（清單標示「使用中」「預設」「編輯中」，載入、儲存、另存新佈局、刪除、套用、回到預設佈局）。不能用的按鈕一律停用，不隱藏。

### 規則

- **載入**：把清單選的那一份讀進草稿（沒在編輯時就進入編輯）；草稿有未儲存的修改時先在確認區塊問。**離開編輯**、**刪除**（一律確認）、**回到預設佈局**（編輯中有未儲存的修改時）同理，不用系統對話框。
- **儲存**（PUT）：預設佈局停用，要另存；草稿沒有修改時也停用。**另存新佈局**（POST）：名稱欄可不填，不填就用「佈局 N」（N 取清單裡最小沒用過的）；成功後草稿改成這份新佈局。
- **套用**：編輯中套用的是草稿——有修改先儲存（PUT）成功才套用；沒在編輯時套用的是清單選的那一份。有錯誤時停用；預設佈局有修改時停用並提示「預設佈局有修改，請先另存」。後端回 409 時確認區塊顯示後端的說明（「工廠還有在製品：…」）與「清空示範資料並套用」「取消」。成功後離開編輯、`LayoutController.Reload()`、重新讀清單。
- **回到預設佈局**：套用預設佈局（同樣的 409 流程）；預設佈局已經是使用中時停用。
- **「已經是使用中」的判斷**：後端允許用 PUT 改使用中的佈局（改了存檔的文件，工廠仍照套用時的版本跑）。清單的使用中佈局有「存了但還沒套用的修改」時套用仍可按；否則停用並提示「這份已經是使用中的佈局」。（原本用 `UpdatedAt` 與 `AppliedAt` 比較，已改成後端的 `HasUnappliedChanges`，見第 10 節「使用中佈局的套用快照」。）
- HTTP 失敗的原因（`LayoutResponse.Message`，含 400 的檢查結果第一條）顯示在頁面最上面的訊息列。
- 按鈕、滑桿、清單在儲存、載入、套用進行中暫時停用。

### 被拿掉的車留在 Broker 上的舊狀態

- 問題（第 7 節「已知限制」）：套用拿掉某台車的佈局後，`LayoutPublisher` 先把那台車的 state Topic 清成空的 retained 訊息，之後又有一筆非空的狀態被發布，Broker 上留著已經不存在的車。

## 11. 第 5 步（上）：共用程式庫的路線編輯（2026-10-25）

第 5 步的純計算部分：路線操作、點選與吸附、驗證標記，都在 `OpenFleet.Layout`，有單元測試。Unity 的路線工具還沒開始。

### 規則

- **`LayoutEditSession` 的路線操作**（成功的一次 = 一步復原；失敗或沒改到東西不留紀錄，和模組操作相同）：
  - `AddRoad(startX, startZ, endX, endZ)`：包 `RoadGraphEditor.AddRoad`，回傳沿線節點代碼；起點終點落在同一個節點、或整條路已存在（文件沒變）時回傳 null。
  - `MoveNode(code, x, z)`：包 `RoadGraphEditor.MoveNode`（0.3 m 內合併），回傳移動後的節點代碼（合併時是被合併到的那個）；找不到、是交接點、位置沒變時回傳 null。
  - `DeleteNode(code)`、`DeleteEdge(from, to)`；`IsHandoffNode(code)`（比對距離與驗證器、`DisconnectModule` 相同，`LayoutRules.HandoffMatch` 0.05 m；`RoadGraphEditor.IsHandoffNode` 是同一份判斷）。
  - 交接點節點跟著模組走：`MoveNode`、`DeleteNode` 拒絕（見決定 1）；它的支線仍可用 `DeleteEdge` 刪，交接點節點會保留。
  - **`RoadGraphEditor.AddRoad` 接到最近的節點**（使用者決定 2026-10-25，互動驗收發現，見第 12 節）：起點或終點落在路段內部、以及每個交叉點，離該路段較近的端點不到 `MinEdgeLength`（1.6 m）時，直接用那個既有端點、不切段（兩端都不到取較近的）；離兩端都夠遠才照樣切出路口。原因：車道節點每 4 m 一個，在節點附近切段會留下過短的路段（`edge-short`、`edge-clearance`）。新的路因此會稍微彎過那些節點。判斷和 `ConnectModule`（第 8 節）共用同一個私有函式 `NearEndpoint`。0.3 m 合併等其他行為不變。
- **點選與吸附 `RoadPicking`**（常數在 `LayoutRules`：`PickNodeRadius` 0.5、`PickEdgeRadius` 0.4、`SnapNodeRadius` 0.6、`SnapEdgeRadius` 0.4、`RoadGrid` 0.2、`MinDrawLength` 1.0）：
  - `NearestNode`、`NearestEdge`（點到線段的距離，回傳文件裡的路段物件）；半徑「小於等於」，容許浮點誤差。
  - `Snap`：0.6 m 內的節點 → 0.4 m 內的路段（投影到路段上）→ 0.2 m 格點；結果取到 0.01 m；回傳 `RoadSnap`（X、Z、Kind、NodeCode、Edge）。
  - `LockAxis`：Shift 鎖軸，保留 |dx|、|dz| 較大的軸（相等保留水平）。`SnapLocked`：鎖軸後只沿鎖定線吸附（決定 2）。
  - `MinDrawLength` 只是常數，「比 1 m 短就不畫」由 Unity 這一側判斷。
- **驗證**：`unreachable` 問題除了 `ModuleCodes`，現在也填 `NodeCodes`（連不到原料倉的模組的交接點節點）與 `Edges`（不在原料倉連通區塊裡的所有路段），讓編輯器能畫紅色。訊息與代碼不變。
- **`LayoutIssueMarks.From(validation)`**：直接依每個問題的嚴重度取 `NodeCodes`／`Edges`／`ModuleCodes`，得到錯誤節點、警告節點、錯誤路段（不分方向，`HasErrorEdge(from, to)`、`EdgeKey`）、錯誤模組。規劃列的錯誤（edge-short、edge-crossing、edge-clearance、edge-through-module、edge-invalid、handoff-missing、unreachable）與警告（node-isolated、handoff-through）和驗證器實際的嚴重度一致；警告問題的路段與模組不標記（`handoff-through` 的警告只標節點）。

- 切換工具會取消進行中的拖曳、畫線、擺放；選取不變。擺放模組（按「新增模組」的按鈕）時如果在畫路線工具，會先切回選取工具。
