# P7 實作紀錄：沙盒佈局

## 1. 範圍與步驟

P7 讓工廠的佈局可以由使用者自己擺：機台、AGV 與 AGV 的路線都模組化，可以依需求增減數量、決定實際擺放的位置，類似沙盒模式。使用者 2026-10-24 決定的規則：

- **每台機台一個模組**：每台車床、每座爐、每個工站都獨立擺放，各有自己的 AGV 交接點與備料區、成品區（車床備料區 30 支，是先前確認過的數值）。AGV 送料時才決定送到同一道工序的哪一台。P6「兩台車床共用一個交接點與備料區」的做法改掉。
- **AGV 路線也由使用者拖曳擺放**；車道不限方向（沿用先前的決定）。
- **工廠清空時才套用**：編輯時工廠照常運轉；按「套用」時如果還有訂單在做，提示可以「清空示範資料並套用」；套用後 AGV 回到各自的車位重新開始。
- 一併要做：**廠房大小可調**、**多份佈局存檔**（另存、載入，並且一定能回到預設佈局）、**裝飾物也能擺放**（雜物倉庫、載具存放區）。
- 不做：一次畫兩條平行車道的畫法、生產中即時改佈局。

實作分成幾步，每一步做完先給使用者看：

| 步驟 | 內容 | 狀態 |

| 1b | 每台機台一個工站：預設佈局的粗加工、精加工各兩台獨立的車床，各有交接點；單台車床的模型；舊資料庫升級 | 完成（第 4 節，待使用者確認） |

## 2. 設計重點

- **佈局**是一份文件：廠房大小、模組（種類、位置、朝向）、路網（節點與路段）。可以存很多份，同時只有一份使用中。
- **模組**分四類：機台（每台一個工站，同一道工序可以放好幾台）；倉儲站（原料倉、成品倉、出貨、刀具庫）；AGV 車位（放一個車位就是多一台 AGV）；裝飾物。
- **套用**＝清空生產資料 → 由佈局推導出站點、機台、刀具、路網與車輛 → 重新載入路網、重置交通控制 → 發布新的佈局版本，模擬器依車輛清單增減車輛、所有車回到車位，Unity 依新佈局重建場景。
- 製程（工序、加工時間、測試倍率）不屬於佈局，仍在示範設定。佈局只決定每道工序有幾台、放在哪裡。
- 後端與 Unity 共用一個佈局程式庫（模組目錄、幾何、驗證、路網編輯、預設佈局），Unity 編輯時的即時檢查和後端套用前的檢查結果一致。
- **送料選哪一台**：
  - 逐件工序（切料、車床、拋光、品管、包裝）：在放得下的站裡，先看換線與批次（沿用 P6 的排名），再看機台能不能馬上做（沒有在等刀、換刀、成品台沒卡住），再看路程，最後看代碼。
  - 整爐工序（淬火、回火、電鍍）：先送到沒在跑、爐前已經有料的爐（料多的先，先湊滿一爐），其次是沒在跑的空爐，最後才是正在跑的爐。

## 3. 第 1a 步：工序與工站分開（2026-10-24）

### 資料表（Migration `SeparateStepsFromStations`）

- `ProcessSteps`：`StationCode` 改名為 `Code`（工序代碼，與原本的站點代碼相同：cutting、rough…），新增 `Name`（工序名稱，從工站的站名回填），`Code` 唯一。不再有到工站的外鍵。
- `Stations.StepSequence`：工站屬於哪一道工序（倉儲站與出貨站是 null）。
- `TransportTasks`：`ToStationCode` 可為空；新增 `ToStepSequence`。檢查條件：目的站與目的工序至少要有一個。送到工序的搬運在待派工時目的站是空的，派車時才定（`BindDestination`）。
- 舊資料不用搬：工序代碼就是原本的站點代碼，舊的加工紀錄、搬運與機台都照原樣接得上。

### 規則

- **搬到某道工序的框**：建立搬運時只記工序（`TransportTask.CreateToStep`）。派車時（`TransportService.DispatchPendingAsync`）：
  1. 目的站放不下的不算，都放不下就繼續等，不占用車輛，也不算缺車。
  2. 有車可派才選站。只有一站就是那一站；有好幾站時由 `StationSelector` 挑：逐件工序依換線排名（站上機台最好的那一台）→ 機台馬上能做的 → 路程 → 站代碼；整爐工序依爐前有沒有料（料多的先，先湊滿一爐）→ 沒在跑的 → 正在跑的（爐前料少的先）→ 路程 → 站代碼。
  3. 選定後和派工在同一筆交易寫入。
- 送到工序的搬運被退回（車拒絕、還沒取料就失敗）時目的站清掉，下次派車重新選。
- **整爐工序**：每座爐各自排隊與開爐（`StartBatchRunsAsync`）。「還會有料來」只算工序在這道工序之前的，或這道工序還在搬運中、還沒定站、或定的就是這座爐的；已經排在別座爐前或爐裡的不算。
- **預估**（`ScheduleForecaster`）：同一道工序的站共用排隊區；已經排在某座站前的框只能由那座站接；整爐每座爐各自算開爐；搬運時間用離來源最近的站。
- **缺車統計**（`VehicleShortageService`）：等不到料以工序為單位，同一道工序所有站的閒置機台、排隊與在送的框一起算。

### API 與 Unity 的契約

- `ProcessStepDto`：`StationCode`／`StationName` 改為 `Code`／`Name`（設定頁的工序清單）。
- `StepDelayDto`：`StepCode`／`StepName`（缺車統計的工序）。規格兩處寫法不同，這裡採用工序的命名（見第 5 節）。
- `TransportTaskDto`、`VehicleWaitDto`：`ToStationCode` 可為空，新增 `ToStepName`（待派工時顯示工序名稱）。
- `StationDto`、`StationStatusDto`：新增 `StepSequence`。
- `MachineScheduleDto`：新增 `StepSequence`（面板依製程順序排機台；原本用站代碼推工序，之後一道工序多站時會錯）。
- Unity：`ProductionPanel` 改用新欄位；待派工的搬運顯示工序名稱；排程的機台排序改用 `StepSequence`。契約 DLL 已用 `unity/sync-contracts.ps1` 同步。Unity 檔案是 CRLF，改動時保留原本的換行。

## 4. 第 1b 步：每台機台一個工站（2026-10-24）

## 6. 第 2 步：佈局資料、驗證與套用（後端＋模擬器）（2026-10-24）

佈局變成資料：預設佈局由程式產生，其他佈局可以存檔、驗證、套用。套用後站點、機台、刀具、路網與車輛都由佈局推導，不再寫死在程式裡。Unity 的場景還是 Editor 產生的（第 3 步才改），所以驗收時最後要套用回預設佈局。

### 資料表（Migration `FactoryLayouts`）

| 資料表 | 變更 |
| --- | --- |
| `FactoryLayouts`（新） | `Id`、`Name`（40 字，唯一）、`Document`（jsonb，和 MQTT、HTTP 共用 `JsonDefaults`）、`IsDefault`、`IsActive`（部分唯一索引）、`CreatedAt`、`UpdatedAt`、`AppliedAt`、`AppliedHash`（文件 JSON 的 SHA-256） |
| `Stations` | 新增 `Kind`（字串）、`X`、`Z`、`Rotation`；`HandoffX`／`HandoffZ` 保留 |
| `Vehicles` | 新增 `HomeX`、`HomeZ`（車位座標，可為空）、`InLayout` |

升級：舊資料的新欄位是預設值（`Kind` 為空、座標 0、`InLayout` 為 false），第一次啟動時由預設佈局推導補上。Migration 只有新增欄位與新表，沒有搬資料的 SQL。

### 規則

- **結構檢查**（`LayoutValidator` 的第一步，問題代碼 `document-invalid`，錯誤）：文件來自 JSON，欄位可以是 null、種類可以是任意整數（`JsonStringEnumConverter` 允許整數），後面的檢查都假設結構完整，所以先擋。檢查項目：文件、`Floor`、`Modules`／`RoadNodes`／`RoadEdges` 為 null；清單裡有 null 的項目；模組或節點的代碼為 null 或空白；模組種類不是定義過的 `ModuleKind`（`Enum.IsDefined`）；路段的 From／To 為 null。有任何結構錯誤就直接回傳（`IsValid = false`），不跑後面的檢查；驗證器在任何輸入下都不丟例外。同一種問題只回一則，列出前 5 個項目的編號（從 1 起），多的用「…（共 N 項）」帶過。只有 null 算結構錯誤，空字串的路段端點照舊是 `edge-invalid`。
- **存檔**（`CreateAsync`、`UpdateAsync`）：在碰資料庫之前先驗證，有 `document-invalid` 就丟 `RequestValidationException("document", 訊息)`（400），不寫入；其他錯誤（重疊、缺工序…）照規格仍然可以存，沙盒常存半成品。驗證結果直接用在存檔後的回應，不再驗第二次。套用與 `/validate` 走驗證器：結構錯誤＝無效佈局，套用回 400，`/validate` 回 200 加問題清單（body 是 `null` 也一樣）。
- **推導**（`LayoutDeriver`，純計算）：工站與倉儲站各一筆；逐件工序的站各一台機台（代碼＝站代碼、編號 1、名稱＝站名）；有刀具的機台各一筆刀具狀態；路網照抄；每個 AGV 車位一台車（`InLayout`、派工）。整爐工序（淬火、回火、電鍍）的爐不是機台。
- **寫入**（`LayoutWriter`）：有的更新、沒有的新增、不在佈局裡的站與機台刪掉。車輛不刪，不在佈局裡的只退出派工（`InLayout = false`、`DispatchEnabled = false`）。路網整份換掉。
- **套用**（`LayoutService.ApplyAsync`）：
  1. 驗證，有錯誤回 400（`LayoutValidationDto`）。
  2. 暫停背景工作（`LayoutGate`），再檢查在製品。完成的框是 Scrapped、Boxed、Shipped，以及在成品倉的 Staged；其他的框、Pending／Assigned／Executing 的搬運、還沒出爐的爐都算在製品。有在製品且 `resetDemo=false` → 回 409（`LayoutBusyDto`）。
  3. 一筆交易：清空生產資料（`DemoData.ClearProductionAsync`，示範重設與套用共用）→ 清 `MachineDelays`、`VehicleWaits` → 寫入推導結果 → 初始庫存 → 這份佈局設成使用中（其他的關掉）→ 記下 `AppliedAt`、`AppliedHash`。
  4. 交易提交後從資料庫重新載入記憶體（`LayoutRuntime`）：路網、交通控制（`Reset`）、使用中的佈局（`ActiveLayout`）、退出佈局的車（`FleetStateStore.SetLayoutVehicles`）。
  5. `LayoutPublisher` 發布新的佈局版本（retained）；不在佈局裡的車清掉它們在 Broker 上的舊狀態（retained 的空訊息）。
- **啟動**（`InitializeDatabaseAsync`）：Migrate → `SeedAsync(db, DefaultLayout.Build())`（預設佈局每次用程式的文件覆寫；沒有使用中的佈局就讓它使用中並推導）→ 使用中的佈局驗證失敗，就改用預設佈局；預設佈局的雜湊和程式不同（程式改了），就重新套用；有在製品時只記錄警告。自訂佈局的文件改過但還沒套用，只記錄警告，不替使用者套用。最後從資料庫載入記憶體。
- **閘門**（`LayoutGate`）：生產、派工、交通三個背景工作每一輪開頭 `TryEnter`、結束 `Exit`；套用時 `PauseAsync` 擋住新的一輪、等進行中的一輪結束。MQTT 事件處理不擋（規格：晚到的事件找不到派工，本來就會被忽略）。
- **模擬器**：收到佈局版本後，新版本（`LayoutId` 或 `AppliedAt` 不同）換新的 `SessionId`，清掉舊的回報與待送事件，每台車放回車位、清掉工作與載貨；同一版本（重新連線時收到的 retained）只增減車輛，不動位置。不在清單裡的車，它的放行與指令一律忽略。例外：啟動後的第一個佈局，設定檔初始清單裡已經存在的車保留原位（仍然換 Session、清掉工作與路徑）；正式執行時初始清單是空的，所以不影響。

### Claude 自己決定的部分（待使用者確認）

1. 套用時先暫停閘門，再檢查在製品（規格的順序是先檢查再暫停）。先檢查的話，檢查與清空之間可能有新的訂單或搬運冒出來。
2. `LayoutGate.PauseAsync` 被取消時會恢復（規格沒寫）。否則取消後背景工作會永久停住。
3. 在製品的判斷：Staged 只有在成品倉才算完成（規格原文）；`BatchRuns` 還沒出爐也算在製品（規格沒列，但爐裡的料仍在流程中）。
4. 啟動檢查：預設佈局的雜湊不同才重新套用；自訂佈局只記錄警告，不自動套用（避免替使用者套用還沒按的修改）。
5. 部分唯一索引：`IsDefault` 也加一份（規格只寫 `IsActive`）。
6. `resetDemo` 查詢參數可以省略（最小 API 會把非可為 null 的 bool 當成必填）。
7. 路網寫入用 `ExecuteDelete` 加分離追蹤：同一個 `DbContext` 連續寫兩次時，追蹤會和新的節點衝突。
8. `LayoutGeometry` 的座標取到 9 位小數：避免 `-3.1999999999999997` 這類誤差，讓站點交接點和路網代碼對不上。
9. 模擬器換新版本時，清掉還沒送出的回報與事件（舊 Session 的，後端會當作重啟忽略）。
10. 交通控制找不到站點節點時先不動車（保守，不替它規劃路徑）。
11. 測試的車號（`agv-a`…）不符合代碼規則，只在測試資料庫裡存在；端到端測試用正式代碼（`agv-01`、`agv-02`）。
12. 結構錯誤的文件一律回 400、不寫入資料庫（規格沒寫）：文件或 `Floor` 為 null、三個清單為 null、清單有 null 項目、模組或節點代碼為 null 或空白、種類不是定義過的值、路段端點為 null。這些在寫入前由 `LayoutValidator` 的 `document-invalid` 擋下來（取代原本只檢查整份文件為 null 的 `RequireDocument`）。其他錯誤（重疊、缺工序…）仍然可以存，照規格沙盒常存半成品。沒有帶 `document` 欄位時，DTO 的預設值是空的文件（結構完整），照規格當成「有錯誤的佈局」存下來。
13. 端到端測試 `Lot_travels_from_raw_store_…` 原本假設同一批的第一框送到 1 號機。兩台車床都空著時，先派出去的框拿到較近的 1 號機，而同一批的框建立時間相同，派工排序靠 `Id`（隨機），所以可能送到 2 號機（單獨跑三次中失敗一次）。測試改成比對工序種類（粗加工、精加工）與搬運順序，不比對是哪一台同類機台；派工的排序沒有改。
14. 模擬器啟動後收到的第一個佈局，設定檔初始清單裡已經存在的車保留原位，不放回車位（仍然換新的 Session、清掉工作與路徑）；之後的新版本一律放回車位。理由：正式執行時初始清單是空的，不受影響；測試與離線用的初始清單可以指定起點，端到端測試才能讓車從離車位很遠的地方出發，驗證交通控制把閒置的車引導回車位（改成由佈局決定車輛之後，這個測試曾經因為車一開始就在車位上而什麼都沒驗到）。保留的是車目前的位置，而不是設定的起點：放行可能在佈局訊息之前就到了、車已經開出去一小段，這時不能把車瞬間搬走。

### 已知限制

- 閘門只擋背景工作。套用時如果有 HTTP 請求同時寫入（例如下單），理論上會有競態。目前是單機單人使用，示範資料可以接受；多人同時用時要再加鎖。
- Unity 場景還是 Editor 產生的，第 3 步才會依佈局建場景。套用非預設佈局之後，Unity 畫面和後端會不一致。（第 3 步已解除，見第 7 節。）
- 佈局的檢查（`LayoutValidator`）只檢查結構與幾何，不檢查車輛能不能實際開到每個地方；那要靠套用後的實際運行（第 6 步的驗收）。

### 規則

- **預設視角**：目標是廠房中心往南 1.5 m（再往西讓出操作面板的位置：距離 56 m 時 1 m，距離越遠偏移越多），距離 ＝ 56 × max(寬 / 76, 深 / 30.4)，限制在 30～140 m。預設佈局（76 × 30.4 m）得到目標 (3, 0, -1.5)、距離 56 m，和第 1b 步相同。廠房大小沒變時（例如只換了機台位置）重建只更新預設視角，不動使用者目前的視角；第一次與大小改變時攝影機一起回到預設視角。（規劃寫的參考大小是 60 × 30.4 m，見下面「Claude 自己決定的部分」第 1 項。）
- **車輛的顯示**：
  - 佈局還沒建好時不顯示車輛（後端沒開時 Broker 上留著舊的 retained 狀態，車會浮在空地上）；建好之後重新取一次快照。
  - 目前的車輛清單（最近一次佈局版本）以外的車一律不顯示：版本訊息到時移除畫面上的車，之後到的狀態也丟掉（原因見「已知限制」的後端問題）。
- **AGV 車位**：Prefab 裡有一個淺藍色的占地框線（原本是充電維護區一個大框，規劃決定拿掉，改成各車位自己的框）；沒有交接點方框（車就停在那個點上），`Handoff Point` 是空的群組；標籤只在編輯模式顯示。
- 場景的名稱：模組物件名稱＝模組代碼，工站與倉儲站就是後端的站點代碼，`StationAnchor` 依名稱對應。

### Claude 自己決定的部分（待使用者確認）

1. **預設視角的參考大小**：規劃寫「距離 ＝ 56 × max(寬 / 60, 深 / 30.4)」，那是第 1b 步把下排拉寬到 8 m 間距（廠房加寬到 76 m）之前的數字；照它算預設佈局會拉遠到 71 m，機台上固定大小的進度條會互相重疊（第 1b 步的已知限制）。改成以預設廠房（76 × 30.4 m）為參考，預設佈局的視角和第 1b 步完全一樣；另外讓目標往西偏移「距離 ÷ 56 m」，延續第 1b 步 X = 3 的決定（讓右邊的操作面板不蓋住切料）。右邊的淬火、回火、電鍍仍被面板蓋住（第 1b 步留下的待確認事項）。
2. **路面畫法**：照規劃每條路段一片鋪面加中心黃線、節點補圓；和第 1b 步內外兩條車道的整片鋪面（外緣與內緣黃線、中間白線）看起來不同，內外兩圈之間會多出約 0.2 m 的地板色縫。位置與路網拓樸完全相同。
3. **AGV 車位**的畫法（規劃只說「Zone」「Handoff Point」「Label」）：淺藍框線（沿用原本充電維護區的顏色）、沒有交接點方框、標籤只在編輯模式顯示。
4. **車輛的顯示規則**：佈局沒建好時不顯示車；不在最新車輛清單裡的車不顯示（規劃只寫「移除不在車輛清單裡的車」）；佈局建好時重新取一次車輛快照。
5. **場景的物件分組**：`Factory` 底下是 `Environment`、`Roads`、`Stations`、`Bays`、`Decor`（規劃只寫根物件 `Factory`）。
6. **材質與 Resources 路徑常數**放在 `PresentationController`（`ModulePrefabFolder`、`LayoutMaterialsPath`、`ModulePrefabName`），模組 Prefab 與材質清單的載入也由它負責，符合「畫面物件統一由 PresentationController 管理」。
7. **編輯模式的節點小圓點**用現有的 `ZoneLine`（白）與 `Handoff` 材質，不另加顏色；`PresentationController.Colors` 的編輯用顏色留到第 4 步。
8. 為第 4 步預先放的接口：`LayoutController.EditMode`、`Reload()`、`LayoutBuilt` 事件、`LayoutScene.Modules`（代碼對應物件）；這一步沒有人用。
9. 貼地的薄片（路面、中心線、節點的圓）不投影；每次重建在記錄裡寫一行建置時間（`Layout built: … in N ms`）。

### 已知限制

- **後端問題（第 2 步，這一步沒改）**：套用佈局時被拿掉的車，它的 state Topic 先被清成空的 retained 訊息，之後又有一則非空的狀態被發布，所以 Broker 上留著那台車的舊狀態。實驗（套用拿掉 `agv-05` 的佈局，用 `mosquitto_sub` 看那個 Topic）：版本 29 之後是空訊息，再來又是一筆版本 30，發布時間在套用後 0.35 秒；另一次實驗查到的留存狀態，發布時間在套用後約 7 秒。後端的 `FleetStateStore.Retire` 已經忽略它的遙測，所以這筆是怎麼來的沒有查。Unity 現在靠車輛清單丟掉它；但別的訂閱者（或沒有這層保護的舊版 Unity）會看到一台已經被拿掉的車。可能的修法：`VehicleStatePublisher` 發布前檢查車是否還在 `FleetStateStore`、不在就不發。需要的話請告訴我是否要在後端處理。
- **套用後車輛回車位的過程**：量過 6 次套用（都在車輛正在跑的時候套用）：2 次後端在 0.5～2 秒內就把車放回車位（後端每 0.5 秒檢查一次要不要發布新版本，加上套用與模擬器處理的時間）；另外 4 次，車輛在套用後的數秒內（最久約 6 秒）仍在路網上移動，最後才停回各自的車位。後端 `/api/vehicles` 的位置也是這樣，所以不是畫面的延遲。其中一次還看到車開到別台車的車位支線上、甚至離開道路的座標（agv-04 在 agv-05 的車位支線上），我推測是套用前後端發出的舊放行路徑在套用後才送到模擬器，這只是推測，沒有查證（模擬器與交通控制的行為，第 6 步的長時間運轉驗收時一起看）。
- 路面畫法和第 1b 步不同（見上）；走道一側的視角沒有另外截圖（不能在使用者的螢幕上操作滑鼠與鍵盤；結構比對已涵蓋位置與尺寸）。
- 操作面板在後端還沒起來時只讀一次設定，之後不會重試：後端晚啟動時，面板的規格選單停在「（讀取中）」、設定頁顯示「讀取設定失敗」，要重開 Unity 才會好（第 3 步之前就有，這一步沒改）。
- 編輯模式、面板的「佈局」頁、`LayoutClient` 的實際使用都在第 4 步；這一步只有 HTTP 呼叫與場景重建。
- 進度條對視角很敏感（第 1b 步的已知限制）：預設視角下剛好不重疊，拉遠就會碰在一起。
- 左上狀態列（IMGUI，預設字型）的中文「等待後端佈局…」看起來像有一條刪除線（截圖放大可見），應該是預設字型沒有中文、改用系統字型的效果；同一列原本只有英文。之後改成用有中文的字型，或改用面板顯示。
