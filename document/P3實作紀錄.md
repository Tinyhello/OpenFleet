## 2. 第一步的設計

### 誰管交通

後端。它持有路網與所有預約，決定每台車的路徑與「可以開到哪裡」；車輛（模擬器）不知道路網，只照放行走。
這和實際 AGV 車隊控制的做法一致（例如 VDA 5050 的 base／horizon）。

```text
TrafficWorker（每 0.2 秒）
  ├ 讀車輛即時狀態（位置、走到路徑的第幾點）
  ├ 讀有效派工 → 決定各車要去哪裡（取料點／卸料點／充電車位）
  ├ TrafficController：規劃、預約、死結處理
  └ 發放行 ── MQTT clearance ──> 車輛沿路徑開到「已放行的最後一點」停下
車輛 ── 遙測（路徑進度）──> 後端釋放它已經離開的節點與路段
```

### 路網

| 項目 | 內容 |
| --- | --- |
| 車道 | 環狀走道內外兩條。外圈中心線 x=±18、z=±6；內圈 x=±16.2、z=±4.2 |
| 節點 | 車道上約每 4 m 一個，加上站點與車位共 59 個，存於資料表 `RouteNodes` |
| 路段 | 75 段，不分方向，存於 `RouteEdges`；啟動時載入記憶體 |
| 車道間連接 | 各站所在的位置有內外車道之間的連接路段 |
| 支線 | 10 個站點交接點（接外圈）、3 個充電車位（接內圈上邊），都只有一個出入口 |
| 安全間距 | 任兩個節點至少相距 1.6 m（大型車的車長），所以「一個節點只給一台車」就足以保證車輛不重疊 |

### 預約與放行的規則

1. 節點與路段同一時間只屬於一台車。車持有「目前所在的節點」到「已放行的最後一個節點」之間的所有節點與路段，通過之後才釋放。
2. 一次最多預約前方 2 個節點（`Traffic:Lookahead`）。
3. 已放行的部分不會收回或更改；改道只換掉還沒放行的部分。因此車輛不會收到互相矛盾的指示。
4. 進入只有一個出入口的支線前，路口與支線要一起拿到；拿不到就停在路口之前，不會堵住路口。
5. 被擋超過 4 秒：把別台車占用的節點與路段排除後重新規劃（例如換到另一條車道）。
6. 互相等待形成循環（死結）：ID 較大的車先嘗試改道；都沒有別的路時，一台先退到旁邊的空節點讓路。改道或退讓之後 3 秒內不再改，避免兩台車讓來讓去。

### 放行的契約

| 項目 | 內容 |
| --- | --- |
| Topic | `openfleet/v1/{factory}/vehicles/{id}/clearance`（QoS 1，不 retained） |
| 內容 | `planId`、`revision`、`path`（依序要經過的點）、`releasedCount`（可以開到第幾個點） |
| 冪等 | 同一個 `planId` 只接受 `revision` 較大的內容；換了 `planId` 表示新的一段路，進度從頭算 |
| 回報 | 遙測帶 `routePlanId`、`routeRevision`、`routeReachedCount`；後端據此釋放路段，並在車輛沒跟上時重送 |
| 不經 Outbox | 放行是隨時會被下一輪取代的控制訊息；遺失了交通控制會自己重送 |

搬運指令不再帶路線：只決定「到了取料點、卸料點要做什麼」。`MoveTo` 指令已移除，回充電車位也是用放行引導。

## 3. 實作時做出的技術決定（Claude，可調整）

| 項目 | 目前做法 | 理由 |
| --- | --- | --- |
| 預約狀態 | 只在後端記憶體 | 和車輛位置一樣是即時狀態。後端重啟後，每台車被放在離它最近的節點上重新開始 |
| 設備重啟 | 遙測的 Session 換了就釋放那台車的所有預約，從最近的節點重新開始 | 模擬器重啟後車的位置會變 |
| 離線的車 | 預約保留 | 實體上還占著那個位置 |
| 讓路的對象 | 死結時 ID 較大的車先讓 | 規則固定、結果可重現；之後可以改成依任務優先順序 |
| 交通控制類別 | 不碰資料庫、MQTT，所有輸入由呼叫端傳入 | 可以單獨測試，包含三台車的壓力測試 |
| 路網資料 | 寫在程式裡的示範定義，啟動時存入資料庫 | 暫定佈局；Unity 的車道位置必須與它一致 |

- 自動化測試 65 個全部通過，連跑兩次穩定。

## 5. 已知限制

- 沒有路權的公平性保證：理論上一台車可能一直被別的車流擋住。目前的規模（2～3 台車）沒有觀察到。
- 改道只看「此刻」誰占著路，不預測別的車接下來要走哪裡，所以可能改到一條馬上又被擋的路。
- 車輛之間的優先權只看 ID，載貨的車不會比空車優先。
- 路徑只求最短，不考慮轉彎或壅塞。
- 後端重啟時，正在兩個節點之間行駛的車會被放到最近的節點，直線開過去。
- 預約以節點為單位，跟車距離至少一個路段（約 4 m）。
- 10 倍速時，放行的速度跟不上車速，車會走走停停。
- P2 留下的限制仍在：搬運失敗後沒有恢復流程、沒有拆批與載具。

## 9. 第二步：缺車紀錄與耽誤時間

### 記錄什麼

| 紀錄 | 資料表 | 內容 |
| --- | --- | --- |
| 缺車等待區間 | `VehicleWaits` | 每個搬運任務一筆：從派工迴圈發現「這個任務可以搬、但整個場地叫不到車」起，到派出車為止 |
| 機台耽誤區間 | `MachineDelays` | 每台機台一筆：等車的任務讓這台機台真的停下來的時間，記錄工序、原因與造成停機的任務 |

兩種區間都保存起訖時間（實際時鐘）與換算成模擬時間的長度；統計用模擬時間，所以切換倍率不會讓數字失真。

### 判定規則（使用者 2026-10-09 確認）

1. 「叫不到車」：任務在等待中、目的站放得下，但沒有可派的車。有車在線但都在忙才是「缺車」；該車型全部離線是重大事故，另外記錄（第 11 節）。
2. 以下都**不算**缺車：目的站放不下而等待（容量）、沒有批次可做（缺料）、派出車之後的行駛與交通等待。
3. 機台正在加工或正在換刀時不算耽誤，就算有任務在等車。
4. 耽誤的兩種原因，按工序分開統計：
   - **等不到料**：要送到這台機台的料叫不到車，而機台沒有東西可做。
   - **成品沒被搬走**：這台機台做完的批次叫不到車，後面排隊的批次無法開始。
5. 同一台機台同一時間只算一次：兩個任務都在等同一台機台，停機時間不會加倍。

### 實作時做出的決定（Claude，可調整）

| 項目 | 目前做法 | 理由 |
| --- | --- | --- |
| 檢查頻率 | 跟著派工迴圈，每 1 秒一次 | 等待與耽誤的起訖誤差最多 1 秒（實際時間）；30 倍速時相當於模擬時間 30 秒 |
| 時間單位 | 模擬時間的秒；每次檢查累加「實際經過秒數 × 當時的倍率」（2026-10-10 整體倍率取消後就是實際秒數，見 P4實作紀錄第 5 節） | 和加工時間同一個基準，才能回答「耽誤了多少加工時間」 |
| 已經有料在路上的機台 | 不算「等不到料」 | 機台等的是那批已派車的料，屬於搬運時間，不是缺車 |
| 等料的機台同時成品也沒被搬走 | 沒有排隊的批次時記成「等不到料」 | 兩種原因互斥，以「有沒有批次在排隊」區分 |
| 車輛全部離線 | ~~算缺車~~ → 使用者 2026-10-10：不算，是重大事故，另外註記（第 11 節） | 缺車只代表車不夠用，不是緊急事件 |
| 後端停機期間 | 重啟後第一次檢查會把停機的時間一起算進去 | 加工進度也是用同樣的方式補算，兩者一致 |
| 清除示範資料 | 缺車紀錄一起清掉 | 紀錄關聯到搬運任務 |

## 10. Unity：物件載入與表演用控制器

使用者的要求是「物件的掛載改由直接讀取 Prefab，Inspector 盡量不掛東西」與「建一個 cs 專門管理物件以及顏色等相關表演用的控制器」。以下是 Claude 的解讀與做法，**是否符合原意待使用者確認**。

| 項目 | 之前 | 現在 |
| --- | --- | --- |
| AGV Prefab | 放在 `Assets/OpenFleet/Prefabs`，由 `FleetView` 的 Inspector 欄位引用 | 放在 `Assets/OpenFleet/Resources/Prefabs`，由 `PresentationController` 以 `Resources.Load` 載入 |
| Prefab 內的參考（燈條、標籤、貨物） | 建 Prefab 時寫進 `VehicleView` 的欄位 | `VehicleView` 啟動時依子物件名稱找到 |
| UI 設定（PanelSettings） | 場景裡的 UIDocument 引用 | 放在 `Resources/UI`，執行時載入；兩個 UIDocument 由控制器建立 |
| 腳本之間的參考（面板 → FleetView、FleetView → 攝影機） | Inspector 欄位 | 透過 `PresentationController.Instance` 取得 |
| 站點對應 | 建場景時把站點代碼與備料／成品物件寫進 `StationAnchor` 的欄位 | 站點物件的名稱就是站點代碼；`StationAnchor` 由控制器在執行時加上，依名稱找子物件 |
| 顏色 | 分散在 `FleetView`、`StatusOverlay`、`ProductionPanel` | 集中在 `PresentationController.Colors` |
| 顯示用的調整值（虛線長度、平滑係數等） | Inspector 欄位 | 各腳本裡的常數 |

- 新的 `PresentationController` 只管「怎麼顯示」：載入與建立物件、保存車輛與站點的對照、定義顏色。它不保存也不推算業務狀態，狀態仍然全部來自後端。
- Inspector 上只留下純數值、而且有預設值的設定：連線位址（`OpenFleet` 物件）與攝影機視角（`Main Camera`）。
- 名稱對應用的字串都定義成常數，建場景的 Editor 程式與執行時的腳本共用同一份，改名不會只改到一邊。
- 模型本身的材質顏色仍在 `Editor/Palette.cs`（建場景時使用），沒有搬到控制器：那些是資源的顏色，不是執行時的表演。
- 已用 Windows Player 驗證：車輛、燈條變色、載貨顯示、站點進度條、面板都和修改前相同。

## 11. 使用者 2026-10-10 的第二次回覆

| 項目 | 決定 | 處理 |
| --- | --- | --- |
| 缺車的定義 | 缺車只代表車不夠用（都在忙），不算緊急；全部離線是重大事故，要另外註記；離線與忙碌是不同狀態，要分開 | 見下方「缺車與離線事故」 |
| 第二步、Unity 的做法 | 沒問題 | 不變 |
| 換刀時間 | 90 秒 | 示範值改為 90；既有資料庫由 Migration 更新（只改還停在 20 秒的） |
| 上下料的意思 | 先前說的「上下料每件 5 秒」是機台從料件拿取、加工後再取出這兩個動作；AGV 是一框一框直接送，把料交給機台、從機台取走一框成品的時間是 30 秒 | 見下方「機台取放與 AGV 交接」 |
| 進度 | 進行第三步 | 見第 12 節 |

### 缺車與離線事故

- 每一筆等車區間、機台耽誤區間都多了「原因」：`VehiclesBusy`（缺車：該車型有車在線，但都在忙）或 `FleetOffline`（重大事故：該車型一台都不在線）。
- 判斷是照任務需要的車型：物料搬運看大型車，刀具配送看小型車。只有一部分車離線、其餘在忙，算缺車。
- 原因改變時（例如離線的車回來了但在忙），結束原本那一筆、另開一筆，兩段時間各算各的。
- `GET /api/shortage` 的缺車數字（`waitingTasks`、`waitSeconds`、各工序的 `delaySeconds`）只算缺車；離線事故另外在 `offlineVehicleTypes`（此刻全部離線的車型，不管有沒有任務在等）、`offlineWaitingTasks`、`offlineWaitSeconds` 與各工序的 `offlineSeconds`。
- 後端的紀錄：缺車是一般訊息，離線事故記為 Error。
- Unity：面板在「缺車耽誤」上方用紅字顯示「重大事故：大型車全部離線」，事故結束後留下累計；機台的加工列在缺車時顯示桃紅色的「缺車」，離線事故時顯示紅色的「離線」。
- 後端剛啟動、模擬器還沒連上時，所有車都是離線；這時如果有等待中的任務，會記成離線事故（事實如此）。

### 機台取放與 AGV 交接

| 設定 | 值 | 意義 |
| --- | --- | --- |
| 機台取放（`pieceHandlingSeconds`） | 每件 5 秒 | 機台加工前從備料區取一件、加工後取出放到成品區，各一次。每件的週期＝5＋加工時間＋5 |
| AGV 交接（`agvHandoverSeconds`） | 一框 30 秒 | AGV 把一框料交給站點、或從站點取走一框，各一次，和件數無關 |

- 原本的設定 `handoverSecondsPerPiece`（AGV 每件 5 秒）改名為 `pieceHandlingSeconds`，值沿用，意義改成機台的取放。
- 以每批 15 件計算：粗加工一批 15 ×（5＋30＋5）＝10 分鐘，精加工 15 ×（5＋60＋5）＝17.5 分鐘；AGV 一趟的交接從原本的 2 × 75 秒變成 2 × 30 秒。
- **待確認**（第 6 節第 6、7 項）：「取、放各 5 秒」是 Claude 的解讀；「一個批次＝一框」也是 Claude 的假定。
- Unity 上車輛的進度條文字從「上料／下料」改為「取貨／交貨」，避免和機台的上下料混淆。

## 12. 第三步：小型 AGV 送刀具

### 流程

```text
刀具剩餘件數 ≤ 門檻（示範 50 件）
  └ 建立刀具配送任務（刀具庫 → 機邊），一把刀只叫一次
      └ 小型車（agv-03）取刀、送到機邊 ── 任務完成＝「配送完成」，新刀在機邊備用，機台照常加工
刀具到達壽命
  ├ 新刀已到 → 開始換刀（90 秒，機台暫停）→ 換刀完成＝另一筆「換刀紀錄」，計數歸零
  └ 新刀還沒到 → 停機等刀 → 新刀送到的那一刻才開始換刀
```

### 規則（使用者 2026-10-09 確認）與實作

| 規則 | 實作 |
| --- | --- |
| 小型 AGV 只負責運送刀具，換刀由其他設備執行 | 刀具配送是一種搬運任務（`ToolDelivery`，沒有批次），只派給小型車；物料搬運只派給大型車。換刀仍由後端的機台模擬執行 |
| 配送完成與換刀完成分開記錄 | 配送完成＝搬運任務完成（`TransportTasks`）；換刀完成＝`ToolChanges` 的一筆。機台另外記錄「已叫刀」「新刀已到」「開始等刀」的時間 |
| 快到壽命時預先叫刀 | 剩餘件數 ≤ `toolRequestThresholdPieces`（示範 50，可在面板調整）時建立任務 |
| 新刀沒到就停機等刀 | 機台停在「等刀」，加工中的批次暫停；新刀送到後從送到的時間開始換刀 |
| 優先順序：完成品 → 送刀具 → 補料 | 排序已照這個順序；目前大型車與小型車各做各的任務，所以實際上不會互搶 |
| 缺車 | 送刀任務叫不到小型車、而機台正在等刀時，記為缺車造成的停機，原因是「等刀」；小型車離線則是重大事故。車已派出、還在路上的等刀時間是配送時間，不算缺車 |

### 實作時做出的決定（Claude，可調整）

| 項目 | 目前做法 | 理由 |
| --- | --- | --- |
| 刀具的來源 | 刀具庫（`tool-store`）有無限的新刀 | 刀具庫存還沒建模 |
| 舊刀 | 換下來的舊刀不回收 | 規劃文件沒有提到回收流程 |
| 刀具交接時間 | 取刀、交刀各 30 秒，沿用 AGV 交接時間 | 使用者只指定了料框的交接時間。**待確認** |
| 小型車的載重 | 一趟一把刀，車速幾乎等於空車 | 車速公式沿用「件數／滿載 30 件」 |
| 派工車輛 | `Fleet:DispatchVehicleIds` 加入 `agv-03` | 小型車要能被派工 |
| 門檻大於刀具壽命 | 換完刀立刻再叫下一把 | 門檻的字面意思；示範值 50 遠小於壽命 500／250 |
| 關閉刀具配送 | 設定 `toolDeliveryEnabled = false` 時視為新刀永遠在機邊（P2 的行為） | 讓只測加工的自動化測試不受送刀影響；面板沒有這個開關 |
| 清除示範資料 | 刀具配送任務與機台的叫刀狀態一起清掉 | 回到剛換好刀的狀態 |
