# P6 實作紀錄：機台排程

## 1. 範圍與步驟

P6 讓機台的安排變成可以設定、可以預估的排程。使用者 2026-10-22 決定的規則：

- 粗加工、精加工各兩台車床，其他站一台。
- 同一站的機台都能做所有規格。
- 排隊的框交期早的先做；負責人可以把某張訂單設成急單，排在所有訂單前面。
- 要有排程預估：每台機台接下來做哪幾框、預估什麼時候做完；每張訂單預估什麼時候做完、趕不趕得上交期。

實作分成幾步，每一步做完先給使用者看：

| 步驟 | 內容 | 狀態 |
| --- | --- | --- |
| 1 | 機台：粗加工、精加工各兩台車床；刀具、換線、加工進度、缺車停機改成每台各自算；Unity 兩台車床的模型與每台一列的進度條 | 完成（第 2 節） |
| 2 | 排程規則：急單、交期優先；面板可以設急單 | 完成（第 3 節） |
| 3 | 排程預估：每台機台的排程與每張訂單的預估完成時間（後端） | 未開始 |
| 4 | Unity 排程畫面 | 未開始 |

## 2. 第 1 步：粗加工、精加工各兩台車床（2026-10-22）

### 資料表

| 資料表 | 內容 |
| --- | --- |
| `Machines`（新） | 逐件工序的機台：代碼（`rough-1`）、所在站、站內編號、名稱（「粗加工 1 號機」；一站一台時就是站名）。粗加工、精加工各 2 台，切料、拋光、品管、包裝各 1 台。整爐工序（淬火、回火、電鍍）一站一座爐，不在這張表 |
| `MachineTools`（取代 `StationTools`） | 每台車床各一把刀：壽命計數、叫刀、送到、換刀、停機等刀 |
| `Operations.MachineCode` | 逐件加工在哪一台做。框在站上排隊時還不知道，哪一台接手才決定 |
| `TransportTasks.MachineCode` | 送刀任務是給哪一台的刀 |
| `ToolChanges.MachineCode`、`MachineDelays.MachineCode` | 換刀紀錄與缺車停機記在哪一台 |

- 一台機台同時只做一框：`Operations` 對「加工中」的 `MachineCode` 有部分唯一索引（`UX_Operations_RunningMachine`），程式寫錯時由資料庫擋下。
- 一台機台同時只有一段進行中的缺車停機（`UX_MachineDelays_OpenMachine`，原本是一站一段）。
- 機台和站點一樣是示範佈局的一部分：啟動時補上缺少的機台、名稱跟著程式裡的命名，面板不能改。

### 規則

- **共用的備料區**：同一站的兩台車床共用一個交接點、備料區與成品區。AGV 把框送到站上，哪一台空下來就由它接手。
- **誰接哪一框**（`MachineAssignment`）：沿用 P4 的規則，但改成每台機台各自看自己的上一框：同批次而且不用換線 → 不用換線 → 同批次 → 同桿徑 → 到站順序。兩台同時空著時，先配排名最好的（機台, 框）組合，所以不用換線的框會交給上一框相同的那一台；排名相同時先到站的框優先、再來是編號小的機台。還沒做過任何一框的機台不用換線。第 2 步會在最前面加上急單與交期。
- **換線**：零件或桿徑和「這台機台」的上一框不同才換。
- **成品台**：每台做完的那一框還沒被搬走，那一台不接下一框；另一台照常做。一站只有一台時，站上任何一框在等搬走都算它的（品管分出來的反工框、包裝站的出貨箱）。
- **備料區容量**：一台車床的備料台 30 支是使用者確認過的數值，兩台車床的站是 60 支。每一框最多算一個備料台：24 mm 一框 45 支比備料台大，占滿一個備料台，但至少放得下一框，所以兩台的站放得下兩框 45 支。
- **刀具**：每台車床各自計壽命、各自叫刀；送刀任務指定給哪一台，小型車送到後只有那一台的新刀到了。
- **缺車停機**改成每台機台各自算，統計時同一道工序的兩台加起來（機台秒）：
  - 等刀：那台機台停機等刀，送給它的刀叫不到車。
  - 成品沒被搬走：做完那一框的機台被它卡住，站上還有框在排隊、沒有別台空著的機台可以接；排隊的框有幾框，最多算幾台。
  - 等不到料：閒置的機台扣掉站上排隊與正在送來的框，就是沒有東西可做的台數；叫不到車的框有幾框，最多算幾台。

### API 與 Unity

- `GET /api/stations/status`：逐件工序的站多了 `machines`，每台一筆（代碼、名稱、編號、加工進度、刀具、缺車停機的原因）。原本在站上的 `machining`、`tool`、`shortageCause`、`shortageReason` 移到每台機台裡。
- 加工紀錄（`GET /api/lots/{id}` 的 `operations`）與機台耽誤區間（`GET /api/shortage/delays`）多了 `machineCode`。
- Blender 模型 `Station_CncLathePair` 取代原本的 `Station_CncLathe`：兩台小型 CNC 車床並排，鐵屑車與冷卻液箱放在機台後方，兩台共用前方的備料台、成品台。西側（預設視角畫面的左邊）是 1 號機、東側是 2 號機，編號標在車床頂上；從走道那一側看過去左右相反。
- 機台上的進度條：備料、成品之後每台一列，兩台時第一欄寫「1號」「2號」，狀態（換線、換刀、缺車…）寫在右邊、用顏色區分；刀具列每台一列。

### 舊資料庫升級

Migration `MachinesAndSecondLathes` 把舊的資料搬過來：每一站原本的那一台變成 1 號機（刀具計數、叫刀狀態、換刀紀錄、已開始的加工、送刀任務、缺車停機都接到 1 號機），粗加工、精加工另外加一台 2 號機（新刀），兩站的容量從 30 改成 60。在本機的資料庫實際升級過：粗加工 1 號機保留了原本的 137 件刀具計數。

### Claude 自己決定的部分（待使用者確認）

- 兩台車床共用一個交接點與備料區（而不是各有一個交接點、搬運時就決定送哪一台）。
- 兩台車床用小型車床的模型放進原本一站的位置，廠房與走道不用改。如果要兩台和原本一樣大的車床，廠房要往東再加寬約 8 m，後段的站與路網跟著移動。
- 兩台的站容量 60 支，以及「一框最多算一個備料台」。
- 缺車停機以機台計，兩台加起來是機台秒；上面三種原因「最多算幾台」的算法。
- 機台名稱（「粗加工 1 號機」）與 1、2 號機的左右位置。

### 驗證

## 3. 第 2 步：急單、交期優先（2026-10-22～23）

### 規則

一框的優先順序（`SchedulePriority`）：急單最先；同為急單或同為一般訂單時，交期早的先；沒有交期的排在有交期的後面。優先順序一樣時，照各處原本的規則。用在四個地方：

| 地方 | 做法 |
| --- | --- |
| 逐件工序的站挑下一框（切料、車床、拋光、品管、包裝） | 優先順序是第一個條件；一樣時照第 1 步的規則（同批次不用換線 → 不用換線 → 同批次 → 同桿徑 → 到站順序） |
| 整爐工序裝爐（淬火、回火、電鍍） | 急單、交期早的框先裝，其餘照到站順序，裝到上限為止。開爐條件不變 |
| 等料的框分配圓棒 | 急單、交期早的先拿到圓棒，其餘照建立順序 |
| 派車 | 搬運種類的順序不變（做完的框 → 送刀 → 補料，使用者 2026-10-09）；同一種搬運裡急單、交期早的框先搬，其餘照建立時間 |

- 框的優先順序看它屬於哪一張客戶訂單：工單的框（含補做工單）看工單的訂單，訂單的出貨箱看出貨單的訂單。沒有訂單的框（測試用的批次、送成品倉的箱子）等同沒有交期的一般訂單。
- 急單由負責人設定，記下名字與時間，可以取消；全部做完或已經出貨的訂單不能設。設了之後下一輪排程就生效。
- 不搶占：已經開始的加工、已經開的爐、已經派出的搬運不會因為急單被打斷，急單從下一個空檔開始優先。

### API

| 方法 | 路徑 | 說明 |
| --- | --- | --- |
| POST | `/api/sales-orders/{id}/rush` | `{"requestedBy": "廠長"}` 設成急單（400 沒有負責人、404 找不到、409 已經是急單或已經做完） |
| DELETE | `/api/sales-orders/{id}/rush` | 取消急單（409 不是急單） |

訂單（`SalesOrderDto`）多了 `isRush`、`rushRequestedBy`、`rushRequestedAt`。資料表 `SalesOrders` 多兩個欄位（migration `RushOrders`）；兩個人同時按由 xmin 擋下後到的那一個（409）。

### Unity 面板

- 下單多了「交期（天後）」滑桿：預設 28 天（一組從下單到完成約三週到一個月），0 表示不填。送出時只帶日期，不帶時區。
- 訂單上方的欄位改名「負責人」，同意分批與設急單都記這個名字。還在生產的訂單多一顆「設為急單／取消急單」；急單的標題標【急單】、用橘色。

### 順便修的問題：同一輪裡拿到舊的框狀態（P5 第 5 步就有）

接真的模擬器跑的時候，後端記錄裡偶爾出現 `Production cycle failed`：某一框明明已經卸到下一站排隊，加工推進卻說它「在車上」不能開始。原因是整張訂單出貨的檢查（P5 第 5 步加的 `BoxOrderAsync`）會把那張訂單所有的框都載入並追蹤，包括還在車上的；那一框在同一輪裡被搬運事件卸到下一站，這一輪後面「空機台開始下一框」拿到的就是先前載入的舊狀態。那一輪會整輪放棄、下一輪就好，所以只是慢了一下，但每次都會記一筆錯誤。

改成只讀還在流動的框的狀態、不追蹤，只追蹤會被裝箱改動的已包好的框（程式裡原本就有這條規則，P5 的這段沒有照做）。新增的測試在修正前會失敗。

### Claude 自己決定的部分（待使用者確認）

- 交期一樣時（或都沒有交期）照原本的換線、同批次規則；多張急單之間也照交期排。
- 派車「同一種搬運裡急單、交期早的先搬」是 Claude 的建議，使用者回「進下一步」，當作同意。
- 沒有訂單的框等同沒有交期；不搶占已經開始的工作。
- 交期預設 28 天、0 表示不填；取消急單不記錄是誰取消（只記在後端的記錄檔）。

### 已知限制

- 派車時，排在前面的框如果目的站放不下，排在後面、同一個目的站的較小的框仍可能先送進去，占掉空間。框大多是整框，影響不大。
- 優先順序只決定「誰先」，不保證先完成：一張單只有幾框時，一趟搬運在路上被交通耽誤，就可能讓交期較早的單晚一點做完（見下面的驗證）。

### 驗證

- 自動測試 163 個（新增 9 個）：排序規則本身（急單 → 交期早 → 沒有交期；優先順序贏過換線，一樣時照原本的換線規則）；車床上急單的框比先到的一般訂單先做；單台的站交期早的先做、沒有交期的最後；淬火爐先裝急單的框；圓棒不夠時急單先拿到；同一種搬運裡急單、交期早的先派，但一般訂單做完的框仍比急單的補料先搬；設急單與取消的 API（記下負責人、重複設定或已做完回 409、沒有負責人 400、找不到 404）；上面那個舊狀態問題的回歸測試。
- 用真的後端加模擬器跑「三張一樣的單」：P24-SQ08 各 30 組（三種都沒有現成備料，全部從圓棒切），依序建立 A（交期 28 天後）、B（交期 14 天後）、C（沒有交期，建立後馬上設成急單）。

  | 條件 | C（急單） | A | B |
  | --- | --- | --- | --- |
  | 不良率 10%（修正前） | 531 秒 | 625 秒 | 636 秒 |
  | 不良率 0（修正後） | 188 秒 | 256 秒 | 271 秒 |

  - 最後建立的急單兩次都最先做完。修正後的那次，後端記錄裡沒有任何 `Production cycle failed`。
  - A 和 B 之間：記錄顯示各站都有照規則排（切料的順序是 B、C、C、C、B、B、A、A、A，B 排第一是因為 C 還沒設成急單時 B 的交期最早；電鍍也是 B 的框先做、先派車），但 B 最後一框從電鍍到拋光的那一趟，車在路上花的時間比其他車長得多，等它到拋光時 A 的三框已經做完了。一張單只有三框，一趟的交通耽誤就決定了先後。
- Unity 面板：用面板下單時交期滑桿設 10 天，訂單的交期是 10 天後；按「設為急單」後標題變橘色、標【急單】，內容寫「急單：廠長 設定」，按「取消急單」恢復一般訂單（API 確認狀態跟著變）。驗證時把不良率暫時改成 0，驗完已改回 10%，示範資料也清掉了。
