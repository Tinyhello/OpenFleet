## 2. 複雜度判斷與建議邊界

整體需求可以分階段處理。最主要的複雜度來源是有限容量、任務相依性與失敗恢復，而非車型數量本身。

| 情境 | 建議處理方式 | 暫不預設的額外範圍 |
| --- | --- | --- |
| 大型／小型車 | 車型能力、載重、尺寸與站點相容性，以資料配置 | 每個車型建立整套獨立派工程式 |
| 不同料箱／托盤 | 分開定義車輛、實體載具、物料與批次 | 換裝必須全自動或有完整機構動畫 |
| 一批料分多車運送 | 需求拆成多個單車運輸任務，追蹤數量與部分完成 | 多車同時抬同一件物品、同步運動控制 |
| 機台中途補料 | 機邊緩衝區、補料門檻、目標量、在途數量 | 第一次就做最佳化預測排程 |
| 刀具耗損補充 | 模擬壽命或剩餘可加工次數，觸發刀具配送 | AGV 到站便視為已換刀；自帶機械手臂 |

多車協同已確認為各車分攤數量：單車可載 30、需求 40 時拆成 30＋10。不包含共同承載同一件物品。若僅一台車可用，其餘需求等待，不能假定一定有第二台車。

### 本輪補充決策（2026-09-26）

- 料箱與托盤位於取料／取件處，完成運送後需歸還，或在下一個相似且相容任務沿用。精確归還點與沿用條件留空待補；物料配送完成和車輛可再次派工需分開判斷。
- .NET 負責所有業務狀態與模擬運算，Unity 顯示。交通模擬確定納入，細節依使用者要求實作後討論。
- 以批量進行；一件產品是一套沖模，包括上沖、下沖與圓形中模。
- 派工順序已定為搬完成品、送刀具、缺料補料。無車時等待並記錄缺車時間與工序；同級排序與等待起訖細節待補。
- 設 AGV 充電維護區；充電門檻、位置、席位與維護耗時留空待补。
- MVP 先跑通完整流程，未定細節保留待補，不要求現在一次決定所有規則。

AGV 到達機床通常只能在本系統中代表「抵達交接點」。應由模擬交接設備確認取放；送料入加工區、成品下料、換刀各是獨立動作。可以簡化為耗時後回報完成，仍需保留責任區分。

依已確認的刀具分工，狀態設計應區分「刀具配送完成」與「設備換刀完成」。建議流程為：產生刀具需求 → AGV 取刀與配送 → 接收端確認交接 → 配送任務完成 → 其他設備執行並回報換刀。換刀失敗不應回滾成刀具尚未送達；是否需再次配送或維修另行判定。具體交接訊息及換刀模擬方式下一步再細化。

## 3. 流程先行：採購與生產

候選流程：模擬需求 → 建立生產工單 → 檢查並預留可用原料 → 缺料時建立採購需求／採購單 → 模擬到貨 → 收料與入庫確認 → 可用料配給 → 搬運及製程執行 → 品管／反工 → 包裝出貨。

非缺料情況直接由預留進入給料。是否可部分開工、到貨是否需檢驗，下一步再定。採購未到貨不能當作可供 AGV 取走的庫存。報價、供應商、審核、金額等細節本輪不展開。

## 4. 機邊 30 件、剩 15 件補料的例子

已確認「30 件」是待加工料容量；完工件另有 30／45 兩種容量，與桿徑粗細有關。桿徑對照與件數按零件／整套計算待補。

以下保留為先前補料情境的候選推導，尚非最終批量規則：「以批量進行」可能是批內逐件加工、整批放行，也可能整批同時投入，兩者對剩 15 件觸發補料不同；需後續確認，不能自行認定。整套產品的三種組件是否分批加工、在哪個節點配套亦待補。

候選規則：容量與補足目標為 30 件，待加工可用量 ≤ 15 件時重新評估。

本次新增補料量 = max(0, min(目標量 − 現有可用量 − 已承諾未入站量, 工單尚需給料量))。

其中工單尚需給料量須先扣除現有料與已承諾給料，避免重複計算；所有數量使用相同物料、批次／工單範圍及單位。已承諾未入站量包含已預留待取與在途量，每筆只計一次。

- 現有 15 件、無待送量且工單仍需要足夠數量：新增補料 15 件。
- 現有 15 件、已有 10 件確定待送：只新增 5 件。
- 無可用倉庫庫存：保留未滿足需求，不能假設會完成運輸。
- 多台車不能同時各自把 15 件缺口視為尚未分配，需以交易保護需求數量與目的站容量預留。
- 指令逾時但交付情況不明時，先對帳；不能直接釋放承諾量再建立重複配送。

新增需求不等於必須一次載走；可依車輛／載具容量拆趟。卸料前仍需重新確認實體空間；加工暫停、任務取消或其他配送都可能改變容量。

「加工到第 15 件」與「剩餘 15 件」只在特定初始狀況下等價，建議以剩餘可用料與供料承諾計算。這個固定門檻不能保證不停機：後續可用消耗速度、搬運／排隊／交接時間與安全餘量決定門檻，並明確模擬時鐘與時間倍率。

## 5. 資料責任與學習重點

| 模型概念 | 責任 | .NET 學習重點 |
| --- | --- | --- |
| VehicleType／Capability | 車型能力與限制 | 組合、資料建模、規則驗證 |
| Carrier | 料箱／托盤實體、容量、目前位置與占用 | 關聯與資源一致性 |
| MaterialLot／LoadUnit | 來源批次與實際搬運包裝；單件亦可是一個搬運單位 | 可追溯性、數量與位置守恆 |
| TransportRequest | 需要搬多少物料，已分配／已交付多少 | 領域規則、部分完成 |
| TransportTask／Assignment | 一次單車運輸與派工嘗試 | 狀態機、重試與冪等性 |
| ReplenishmentPolicy／StationBuffer | 觸發門檻、目標與站點容量 | 策略、背景工作與併發控制 |
| ToolSupplyRequest | 刀具配送需求及機台相依性 | 不同業務來源共用搬運服務 |

選車先驗證「能不能做」，再比較「誰比較合適」。不能只用大小型標籤或最近距離：需考量載具、重量、站點交接相容性；路線尺寸等更細限制可逐步加入。

批次識別與運輸包裝分開；同批 60 件分三趟各 20 件，仍可保留原批號。失敗的一趟獨立處理，不重做已確認交付的其他趟。

建議學習順序：單車固定載具 → 多車型能力篩選 → 一需求多趟與部分完成 → 站點容量及補料 → 刀具需求 → 換裝流程。首階段可預先配置載具；自動換裝站需額外管理相容性、可用載具與換裝耗時，待核心穩定後再加入。

## 6. 上雲展示選項

Unity 用戶端、後端部署與展示入口是三個可分別決定的問題。Unity Web build 是瀏覽器執行用戶端，不等於把 Unity 畫面放在雲端 GPU 遠端執行。

| 選项 | 訪客如何看 | 取捨 |
| --- | --- | --- |
| A. 雲端後端／模擬器＋輕量網頁看板＋桌面 Unity（建議） | 網址看 2D 位置、任務、庫存與事件；Unity 3D 另以錄影或現場展示 | 可驗證後端且保留 Unity 經驗；新增一個小型網頁介面，限制其範圍 |
| B. Unity WebGL＋雲端後端 | 網址直接操作 3D | 需驗證套件、浏览器通訊、載入大小與效能；無須預設雲端 GPU |
| C. 桌面 Unity＋展示影片＋雲端 API | 影片理解全貌，API 展示後端；需要時下載 Unity | 初期成本與開發範圍較低，但訪客即時體驗較有限 |
| D. 雲端 Unity 渲染串流 | 瀏覽器收畫面及傳操作 | 額外處理渲染主機、串流、工作階段與成本，本案首期不建議 |

方案 A 的資料流提案：.NET 設備模擬器 ↔ MQTT Broker ↔ ASP.NET Core／資料庫；桌面 Unity 經 HTTP 操作與 MQTT 接收狀態；網頁經 HTTP 讀取或提交有限操作，依需求用 SignalR 更新。

網頁初期可先輪詢快照，確認需要即時推播再加入 SignalR；不把完整 3D 場景重做在網頁。網頁框架與雲端供應商暫不選定。

無論展示入口選哪個方案，已確認模擬時鐘、設備運動與加工進度由 .NET 持有，Unity 僅呈現。調度邏輯仍需等設備模擬回報，不能自己發指令後直接判定成功；是否拆為獨立程序待技術設計。

公開展示先考慮共用唯讀情境。若需要訪客派工，另定每人獨立情境或受限操作與重設機制，避免多個訪客互相影響。以上皆為候選，不代表已核准部署。

參考：[Unity Web build](https://docs.unity3d.com/6000.0/Documentation/Manual/webgl-building.html)、[Unity Web 網路限制](https://docs.unity3d.com/6000.0/Documentation/Manual/webgl-networking.html)、[ASP.NET Core SignalR](https://learn.microsoft.com/en-us/aspnet/core/signalr/introduction?view=aspnetcore-10.0)。方案取捨為本專案的設計判斷。
